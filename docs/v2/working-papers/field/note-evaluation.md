# The owner's note of 6 November 2026, checked against the code

An agent on the one real install wrote a note on 2026-11-06, without access to eva-md's source. It records what that agent saw, asks how each stage of memory is timed, proposes eight improvements and lists eighteen acceptance tests. The note is private and is not in this repository. This paper refers to its points by id and describes them in general terms.

Five readers each took one theme, read the v1 code and the v2 plan, and gave every point a verdict. A second reader per theme then tried to prove the first wrong; where it corrected something, the correction is given and it is the one to trust. A researcher read Codex's source at release 0.167.0 for how its voice mode hands work to the agent; nothing was run on a real host, so those findings are leads until the host sitting (HF-00) confirms them.

[The plan](../../plan.md) governs. Its section 14 holds the lead's reading of this paper and what it changed. The installed release the note describes is 2026.11.5 (commit 4f5fa2c); line numbers are from the checkout at 2026.11.7 (commit 51b241c).

Ids: O1 to O10 are the note's observations, S1 to S8 its questions about each stage, A to H its proposals, T1 to T18 its acceptance tests.

## Capture, persistence and when history becomes searchable

### O1. The capture health check passed and recent prompt and tool hooks were seen, which shows capture is active for the chat inspected but not that every surface is covered.

**Verdict:** probably right, and nothing measures it.

**What v1 does.** The capture-freshness row passes when some hook of that host ran in the last 24 hours and the host's own chat folder shows no activity more than five minutes newer than the newest hook of any event (internal/health/watchdog.go:131-184). It is one row per host, read from folder dates and heartbeat files, and compares no turn or tool call with what was stored. A heartbeat is written as a good run even when the hook kept only an event's name, or nothing, because the chat was paused or transcript recovery was behind (internal/hook/hook.go:350-357, 494-505). v1 captures nothing in cloud sessions, excluded or temporary folders and a few host housekeeping folders (hook.go:281-286, 308-315, 335-341), and a surface that loads no plugin hooks is invisible to it. So the note's stated limit is right: PASS shows that hooks fire, not coverage.

Evidence:

- internal/health/watchdog.go:131-184: PASS means a hook ran within 24 hours and no chat-folder activity is over 5 minutes newer than the newest hook of any event; per host, from folder dates and heartbeats only.
- internal/hook/hook.go:350-357: the heartbeat records failed=false unless the run panicked or could not store. hook.go:494-505: a paused chat, or one whose recovery pass is behind, keeps only the event's fixed name; Stop, PostToolUse and UserPromptSubmit have none (hook.go:657-675).
- internal/hook/hook.go:281-286, 308-315, 335-341: never captured: eva-md's own runs, cloud sessions, excluded, temporary, wiki and state folders, a host's memory-writing runs, desktop spares. hook.go:518-521: a headless Claude Code chat's prompts are stored as a host_prompt event with no text.
- internal/install/templates.go:71-88: the hook events each plugin declares.
- 2026.11.5 against 2026.11.7 (git diff 4f5fa2c 51b241c): the freshness rule is the same (git show 4f5fa2c:internal/health/watchdog.go, lines 116-119). 2026.11.7 added the stamp for runs in folders eva-md does not capture, the run's duration in the heartbeat, and WebSearch to Claude Code's tool matcher (internal/install/templates.go), so on the installed release a web search in Claude Code left no line.

**What v2 as planned does.** Section 8, the Stage 0 counters package (LG-01, LG-02, DV-01, DL-02, HO-02): 'How often v1 holds an event back; turn and tool coverage against the host's own record' and 'every session by class'. Section 6.1 bar: 'at least 99.5% of turns and 99% of tool calls in the host's own record are in eva-md's'. HF-00 records real payloads per host. HO-12: 'Health that sees missing work'. Section 12 defers surfaces with no hooks ('A floor for hosts with MCP and no hooks', 'Cloud sessions').

**What is still missing.** Coverage is measured per host, and only for sessions eva-md already holds a file for, against a host record it can read. A session or surface that fires no hook produces no row, so 'not covered' still reads as silence. Nothing in status names the surfaces left out.

**Proposed change.** Amend the gate of the Stage 0 counters package (section 8): 'It also counts, per host, the sessions in the host's own chat store during the counted week that have no eva-md session file, and reports each coverage rate by entrypoint where the host gives one.'

**Second reader:** corrected. The reading of PASS is right: it shows hooks fire, not coverage (internal/health/watchdog.go:137-184; internal/hook/hook.go:350-357, 494-505). Three details are wrong or missing. (1) "The freshness rule is the same" on 2026.11.5 holds for the comparison only. The installed release walks the whole chat store with caps of 512 folders and 4,096 entries and returns UNKNOWN "host activity scan unavailable or incomplete" past them (git show 4f5fa2c:internal/health/watchdog.go:149-152, 170-230, caps at 184 and 201). The checkout reads only the two newest day folders on Codex, or the project folders changed in the past day on Claude Code (watchdog.go:204-305). At the real install's rate (589 Codex session files in about six days, plan section 13.1) the installed row stops being PASS within weeks, for a reason unrelated to capture. (2) On the checkout a PASS can rest on the uncaptured stamp alone, a hook that ran in a folder eva-md does not capture (watchdog.go:148-152, 176-178). On 2026.11.5 the same run left no stamp, so it could raise a false FAIL. (3) Not considered: the activity signal is a folder date, which changes when a chat file is created and not when one grows (watchdog.go:131-136). Hooks that stop during a long chat leave the row at PASS for up to 24 hours and then UNKNOWN, never FAIL, until a new chat file appears. Also, the doctor's per-event rows already say "transcript unavailable for catch-up" and the entrypoint for the newest run (internal/health/health.go:184-193; on 4f5fa2c, health.go:181-182), so a heartbeat row does say more than that a hook ran. It fits LG-02's read-only audit command (working-papers/design/ledger.md:728), whose gate compares a session's transcript with its inbox and does not promise to list host sessions that have no inbox file. Add two conditions: count by file name only, without opening transcripts of excluded folders; and report sessions left out by design (excluded, temporary, cloud, spare folders: hook.go:281-341) separately or as an upper bound, or the count will over-report.

### O3. An index refresh was run by hand before the search that found the item, so the check did not show whether new history is searchable without one.

**Verdict:** already works in v1.

**What v1 does.** Nobody has to run eva-md index for a new line to be found. Search takes candidates from the index for what it covers and scans the rest: session files the index lacks whole, and the tail of each file past where the index stopped (internal/resume/search_index.go:214-277; internal/resume/search.go:352-361). A line can be found as soon as its hook has appended it with its newline. The index itself is refreshed by the daily maintain's last step, by eva-md index on demand, and by a command-line search once 4 MiB or more is missing (cmd/eva-md/maintain.go:105; cmd/eva-md/index.go:18-24; search_index.go:515-560). A test builds the index, appends a line and finds it with no refresh (internal/resume/search_index_test.go:140-163).

Evidence:

- internal/resume/search_index.go:214-277 (classify): a file the index lacks is scanned whole; a file it covers in part has its tail scanned from where the index stopped.
- internal/resume/search.go:352-361: the files and tails left by the index are scanned in the same search. search.go:541-543: only an unterminated last line is left unread.
- cmd/eva-md/index.go:18-24: 'Search works without it, scanning what it doesn't cover.' internal/searchindex/doc.go:14: hooks never read or write the index; doc.go:47-52: the top-up bounds.
- internal/resume/search_index_test.go:140-163 (TestSearchMixesIndexAndTail).
- internal/health/searchindex.go:26-35: the doctor's PASS row says 'covers X of Y MB of the inbox (N%)' and does not say the rest is scanned; only the no-index and damaged rows say so (lines 21, 25).
- README.md:23 and :178 say the index is optional.
- Same on 2026.11.5: git diff 4f5fa2c 51b241c shows no change in internal/resume/search_index.go or internal/inbox/inbox.go, one label string in internal/resume/search.go, and only a new hold.go (for inbox clear) in internal/searchindex.

**What v2 as planned does.** DL-13: 'Matches across a turn, needs no 90-day window; the search index's own scorer is kept'. The area design keeps the tail match ('Indexed turns and the not yet indexed tail are matched by the same tokenizer', deliver.md 3.9). The AGENTS.md rule that the index is a cache is kept.

**What is still missing.** Two small things. The plan does not say who brings the chat index up to date once v1's daily job is deleted at CUT-4, and DL-13's gate does not carry v1's tail test forward. The health row for a partly covered index reads as if the uncovered part were unsearchable, which is the likely reason an agent ran the command.

**Proposed change.** Amend DL-13's gate: 'An event released after the last index build is found with no refresh, by test; the worker brings the index up to date after each pass; and the status line for the index says that what it lacks is still searched.'

**Second reader:** corrected. The v1 reading is confirmed: search scans whole files the index lacks and the tail of files it covers (internal/resume/search_index.go:221-277; internal/resume/search.go:352-361), the test at internal/resume/search_index_test.go:140-163 holds it, and only the no-index and damaged health rows say the rest is scanned (internal/health/searchindex.go:19-35). Two corrections. (1) The gap "the plan does not say who brings the chat index up to date" is true of plan.md only. The organizing design lists "the index refresh" among the worker's timed steps, priority P4, "per tick, when due" (working-papers/design/derive.md:149), and the recall design's DL-13 gate already has "The index equals a brute-force pass over ledger.Walk on fixtures" (deliver.md:913), with the tail matched by the same tokenizer (deliver.md:195). (2) Not considered: the index is not neutral to results. In the files it covers, a match inside a word, in text without spaces, or a rarer exact-case hit can be left out when other hits are found (search_index.go:21-29; internal/searchindex/doc.go:6-10). Running eva-md index before a check can therefore change which hits come back, not only how fast. A repeat of the note's check should search first and refresh afterwards. The proposed change is too large. Keep the first clause in DL-13's gate (an event released after the last build is found with no refresh). Drop "the worker brings the index up to date after each pass": derive.md:149 already makes the refresh a timed worker step, and the tail scan makes a per-pass refresh unnecessary. Move the status wording to the hosts track: status rows are internal/health's (plan section 8, "What runs in parallel"), so it belongs in HO-12 or HO-24, not DL-13.

### S1. Which lifecycle events store something at once, and whether capture also depends on a stop, a session end, a compaction or a timer.

**Verdict:** already works in v1.

**What v1 does.** Capture is a combination of events, each stored inside its own hook run, and nothing is periodic. A prompt is stored at UserPromptSubmit, one line per matched tool call at PostToolUse or PostToolUseFailure, the final reply at Stop, the host's summary at PostCompact (Claude Code only), and fixed event names at SessionStart, SessionEnd, PreCompact, StopFailure, a model switch and Codex's Interrupt (internal/hook/hook.go:513-572, 657-675; internal/install/templates.go:71-88). Only the final reply waits for Stop; prompts and tool lines are on disk before it. Text between tool calls, tool output, and the prompts of subagents or of a headless Claude Code run are never stored as text (hook.go:518-521, 528-535, 781-881). A program-run chat is detected on Claude Code only (hook.go:699-708), so on Codex a prompt a program wrote is stored as the user's typed prompt unless it carries an agent id, a listed source or a listed prefix (hook.go:679-694).

**Second reader:** confirmed. The proposed change is too small. ### S2. Whether storing is synchronous or queued, what survives a crash, and whether a repeated event is stored once.

**Verdict:** a defect in v1.

**What v1 does.** The write is synchronous inside the hook: one append under the session lock and the file's lock, with prompts and replies flushed to disk with their folder before the hook returns, and tool, plan, event and summary lines written without a flush (internal/inbox/inbox.go:158-211; internal/hook/hook.go:361-365). Nothing is queued, so a hook that runs out of its 300 ms (1.5 s at a chat start and for tool events) stores nothing (hook.go:214-219, 229-235). A kill in mid-write leaves a partial last line that readers skip and the next append closes with a 'gap: interrupted append' event (inbox.go:176-196, 356-358). There is no idempotent append: the hook looks for a copy only when its own recovery pass has just stored rows, and only for prompts and replies (hook.go:573-581), and a copy is known by turn plus role, or by role, text and the second of its time (internal/catchup/catchup.go:1382-1390, 1479-1498). So the same payload delivered twice is stored twice, and a reply held by both the transcript and the Stop payload is stored twice when no turn id links the two and their times fall in different seconds.

Evidence:

- internal/inbox/inbox.go:166 (file lock), 200-202 (one write), 203-210 (flush only for role user or assistant), 176-196 (partial last line closed and marked), 356-358 and 412-413 (an incomplete last line stays unread), 420-423 (a malformed line becomes a gap entry).
- internal/hook/hook.go:573-581: the copy check runs only when recovered > 0 and the role is user or assistant; tool, plan and event lines are never checked.
- internal/catchup/catchup.go:1382-1390 (keys), 686-690 (recovery's rule), 1479-1498 (the hook's check), 1411 (only the last 1 MiB of the session file is compared). internal/catchup/parser.go:34: the parser's turn is not carried from one pass to the next, so a recovered reply often has no turn id.
- The audit holds the same reading as finding CUP-09 (docs/v2/findings.md:116).
- What the code cannot settle: which path made the 30 exact repeats in the largest session, or whether they are copies at all (the same command run twice is a true repeat). Every entry carries an origin field, hook or catchup (inbox.go:42), so a count of the repeats by kind and by pair of origins settles it with no new release.
- Same on 2026.11.5: no change in internal/inbox/inbox.go or in these parts of catchup.go and hook.go (git diff 4f5fa2c 51b241c).

**What v2 as planned does.** LG-10: 'a second copy of an event has the same id, so it is dropped'. LG-21's gate: 'no duplicates'. Section 13.3 point 8. Section 6.1: 'A hook waits on nothing but its own small write'; redaction before disk and the fail-closed hook shell are kept.

**What is still missing.** LG-10 gives an event the id 'session and sequence' and section 6.1 says that for v1's files 'the sequence is the line number', so two copies on two lines cannot share an id unless sameness is defined by something else, and the plan does not say what. No gate tells a re-delivered event from a true repeat, so the fix could drop real events. The cause of the repeats on the real install is not known.

**Proposed change.** Amend LG-10's gate: 'The spec states the key that makes two events the same (the host's row id where there is one, else turn id, kind and tool-use id or text). On fixtures, a payload delivered twice and a reply held by both the hook and the transcript each yield one event, and the same prompt typed in two turns and the same command run twice yield two; the reader reports how many copies it dropped per session.' A fact to settle in the second report: of the exact repeats in the largest session, how many are prompts or replies, and how many pair a hook line with a recovery line (two numbers).

**Second reader:** corrected. The synchronous append, the flush for prompts and replies only, and the partial-line handling are as stated (internal/inbox/inbox.go:158-211, 356-358, 420-423); those two parts of the question are implemented and working. The defect is the dedupe part only, and it is a documented limit (docs/known-limitations.md:39). Corrections. (1) "A hook that runs out of time stores nothing" is too strong. Capture runs in a goroutine; when the deadline wins, the hook delivers nothing and is counted as failed, but a line already appended stays (hook.go:209-219, 578; internal/hook/resume.go:338-351). (2) Missing duplicate case: the hook's check skips the text comparison for text over 48 KiB (internal/catchup/catchup.go:885-888, 1487-1491), the documented case. (3) Missing opposite failure: a recovered row whose turn id and role are already stored is skipped before its text is looked at (catchup.go:602-604, 1484-1486), so a second reply in one turn is dropped; the audit's CUP-09 names both sides. (4) On an ordinary Stop with a readable transcript v1 keeps the transcript's copy (origin catchup) and drops the payload's (hook.go:573-581; ledger.md:281 says the same). (5) "The plan does not say what" makes two events the same is true of plan.md only. The record design defines a dedupe key separate from the id: "the host row id and an index, or for hook-only events a hash of turn id, kind and tool-use id or text" (working-papers/design/ledger.md:273, field `src.key` at :108), with `seq` assigned at release (:96). The real gap is that plan section 6.1 keeps v1's files with sequence equal to line number while LG-10 says a copy "has the same id", and the key was not carried into the plan. A gate on LG-10 is the right size and place. Word it as carrying ledger.md:273's key into the spec, and add two fixture cases: two replies in one turn yield two events, and the same command run twice in one turn on a host that gives no tool-use id yields two (the design's fallback key of kind plus text would merge them). The fact to settle from the origin field (inbox.go:42) is sound; add a third number, the repeats that are tool lines.

### S3. When a stored line becomes searchable, and whether the index is refreshed incrementally, at maintenance or on demand.

**Verdict:** already works in v1.

**What v1 does.** A line is searchable as soon as it is on disk with its newline, because search scans whatever the index does not cover (internal/resume/search.go:352-361; internal/resume/search_index.go:214-277). The index is refreshed in all three ways: by the last step of the daily maintain, which the day's first hook event starts (cmd/eva-md/maintain.go:105; internal/hook/maintain.go:55-59), by eva-md index on demand, and by a command-line search once 4 MiB or more is missing (search_index.go:515-560). Hooks never touch it. The limits that do apply are others: only prompts, replies, tool and plan lines are searched (search.go:603-607), the default window is 90 days (cmd/eva-md/commands.go:173), a search stops after 5 s and says so (commands.go:32; search.go:1034-1036), and a match is one line with the exact words.

- internal/searchindex/doc.go:14, 19-21, 47-52.
- cmd/eva-md/maintain.go:78, 105 (the index step, with or without a wiki); internal/hook/maintain.go:55-81 (started by the day's first hook event).
- Same on 2026.11.5 (see O3).

**What v2 as planned does.** DL-13: 'Matches across a turn, needs no 90-day window; the search index's own scorer is kept. A result shows one speaker's words under that speaker's name'. DL-05 gives one tokenizer. DL-12: 'a call has a time bar on both routes'.

Amend HO-12's gate: 'The stages include checked, between capture and organizing, with its own budget.'

**Second reader:** corrected. The cross-cutting claim that v1 has no such state is one-sided: v1's counterpart is that the hook stores only an event's name while its recovery pass is behind, and tool lines dropped that way are never recovered (hook.go:494-505). The proposed change is in the wrong place. ### S4. What schedules the model-based update, and whether there is a debounce, an idle threshold, a need for the session to close, or a batch boundary.

**Verdict:** the designed delay, not a fault.

**What v1 does.** Hooks start a detached eva-md update and forget it; there is no timer and no queue. ## How Codex's voice mode hands work to the agent

Read from Codex's source at release 0.167.0 and from the hosts' documentation on 2026-11-10. Nothing was run on a real host.

**1. What exact text does the agent receive as its input when the front voice model hands work over (envelope shape, latest request, transcript delta)?** (read in the source)

The coding agent receives one user-role text message, built by Codex core, with this exact shape (two-space indents, newlines as shown):

<realtime_delegation>
  <input>LATEST REQUEST</input>
  <transcript_delta>user: ...
assistant: ...</transcript_delta>
</realtime_delegation>

- `<input>` is the front model's hand-over text. In realtime V3 (the `gpt-live-1-codex` model, which the 0.167.0 terminal UI uses) it is the `input_text` of a `delegation` item with `target: "client"`. In V2 it is the argument of the front model's `background_agent` function call. In V1 it is `input_transcript` of a `conversation.handoff.requested` event. If it is empty, the transcript is used in its place.
- `<transcript_delta>` is present only when non-empty. It has one line per utterance, `role: text`, with roles `user` (the person's speech, transcribed) and `assistant` (the front model's spoken replies). It holds everything said since the previous hand-over: the entries are taken and cleared at each hand-over, and the hand-over input is appended as a `user` line when it is not already there. So yes, it carries both the latest request and both speakers' utterances.
- `&`, `<` and `>` are escaped as `&amp;`, `&lt;`, `&gt;`.
- Each field is capped at 4 KiB after escaping, with `…` as the cut marker: the input keeps its start, the transcript keeps its end. In V3 the transcript is not cut.
- A variant carries an extra first line, `  <source>transcript_tail_flush</source>`, with a fixed input: "The user just ended their realtime session. Here is the remaining handoff/transcript tail. You probably do not have to do anything; acknowledge the handoff unless the transcript itself asks for something."

Tests assert the exact string, for example `<realtime_delegation>\n  <input>delegate this</input>\n  <transcript_delta>user: hello\nassistant: hi there</transcript_delta>\n</realtime_delegation>`, and an app-server test asserts that this text is what reaches the model request. The shape is unchanged since at least 0.125.0 (2026-04-24); the `<source>` line dates from 0.145.0 (2026-07-21, PR #33855).

**1 (continued). How is the hand-over delivered to the agent, and what else does the agent see about the voice call?** (read in the source)

Core routes the envelope as ordinary user input on the same thread the voice call is attached to: `route_realtime_text_input` submits `UserInput::Text` in start-or-steer mode, with the turn's trigger set to `"realtime"`. If no turn is running it starts a regular turn; if one is running, the envelope is steered into it. The envelope is not in the list of hidden context fragments, so history treats it as a real user message.

While a call is active the agent also gets a developer message wrapped in `<realtime_conversation>` tags. Its default text begins "Realtime conversation started. You are operating as a backend executor behind an intermediary. The user does not talk to you directly..." and says routed user text is a transcript that may be unpunctuated or contain recognition errors. After the call a matching "Realtime conversation ended." message follows. A client may replace both texts through `realtimeStartInstructions` and `realtimeEndInstructions`.

The `clientManagedHandoffs` start option, which the 0.167.0 terminal UI sets to true, only affects the opposite direction (how the agent's answer returns to the front model). The envelope is routed to the agent either way.

**2. Which hook events fire for a handed-over turn (session start, prompt submitted, tool use, stop, session end, compaction, interrupt)?** (read in the source)

A handed-over turn is a regular turn, and nothing in the turn or hook code special-cases the realtime trigger. So it fires the same hooks as a typed turn:

- SessionStart: only if one is pending, that is, the hand-over is the thread's first regular turn after start, resume, clear or fork, or the first after a compaction. The `source` values are startup, resume, clear, compact and fork; there is no voice value.
- UserPromptSubmit: yes, once per routed envelope, including an envelope steered into a turn that is already running. A hook that blocks it blocks the hand-over.
- PreToolUse, PermissionRequest and PostToolUse: as for any turn.
- PreModelRequest and PostModelRequest (since 0.164.0): as for any agent model request.
- PreCompact and PostCompact: if the turn compacts.
- Stop: when the turn ends, with the agent's last message.
- Interrupt (since 0.150.0): if the running turn is interrupted, on a main thread only.
- SessionEnd: not per turn. It fires only when the thread is torn down.

This follows from reading the code path (routed input, regular task, `run_turn`, `run_hooks_and_record_inputs`). There is no test in the repository that runs hooks on a realtime-routed turn, so a live check is still worthwhile.

**2 (continued). Does the prompt-submitted hook's payload carry the envelope as the prompt, and does any hook payload field say the prompt came from a hand-over, a subagent or a program?** (read in the source)

Yes, the envelope is the prompt. The UserPromptSubmit payload's `prompt` is the concatenated text of the submitted user input, so for a hand-over it is the whole `<realtime_delegation>...</realtime_delegation>` string, escapes included.

No field marks the origin. The UserPromptSubmit command input has exactly these fields: `session_id`, `turn_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`, `permission_mode`, `prompt`, and optionally `agent_id` and `agent_type`. There is no source, origin or trigger field, and no other event's payload has one. `agent_id` and `agent_type` appear only when the hook runs inside a thread-spawned subagent; they say where the hook ran, and are absent on a main thread whatever the prompt's origin.

What a hook or a transcript reader can use instead:
1. The prompt text itself begins with `<realtime_delegation>` and ends with `</realtime_delegation>`. The terminal UI recognises voice turns the same way.
2. The rollout's persisted `turn_started` event carries `turn_attribution.turn_trigger`, which is `"realtime"` for these turns. A test confirms the same value in the `x-codex-turn-metadata` request header.
3. Stop and Interrupt handlers of the MCP-tool kind receive that turn metadata in the call's meta; command hooks do not.

Other trigger values seen in the source are `memory_consolidation` and `daemon_recovery`.

**3. Do exchanges that never leave the front model (the person speaks, the front model answers, nothing is handed over) reach any hook?** (read in the source)

No. The realtime modules contain no hook call at all: a search for "hook" in `realtime_conversation.rs`, its submodules, `realtime_history.rs`, `realtime_context.rs` and `realtime_prompt.rs` at 0.167.0 finds nothing. **3 (continued). Do front-model-only exchanges reach the rollout or transcript file on disk?** (read in the source)

Yes in 0.167.0, for a normal saved thread; no in mid-2026 releases.

From 0.150.0 (2026-08-26, PR #40508 "Persist realtime events in the thread timeline"; moved into core in 0.153.0, 2026-09-02, PR #41924) the thread's rollout gets `realtime_item` lines. Each finished utterance of either speaker is written as, for example, `{"type":"realtime_item","payload":{"id":"...","realtime_session_id":"...","type":"transcript_segment","role":"assistant","text":"hello"}}`. The other payload types are `realtime_session_started`, `bem_item_promoted` and `realtime_session_closed` (with `outcome` `ended` or `failed`). A core test with a call that has no hand-over finds started, assistant segment, user segment and closed in the stored history.

Conditions: the thread must be in the `paginated` history mode and not ephemeral. The terminal UI asks for that mode for saved threads since at least 0.150.0, and the app server defaults to it since at least 0.155.0 when the local store has its state database. In `legacy` mode the items are dropped. The raw realtime events themselves (`RealtimeConversationStarted`, `...Realtime`, `...Closed`) are never persisted in either mode.

Two more ways voice text reaches the rollout as user-role `<realtime_delegation>` messages without any model call or hook:
- 0.167.0 (PR #58221), V3 only: once the not-yet-handed-over transcript passes 4 KiB, completed utterances are saved as an envelope with an empty `<input></input>` and a `<transcript_delta>`, inside a zero-length recorded turn.
- The end-of-call tail, if the client asked for it (see question 4).

Up to 0.145.0 (2026-07-21) none of this existed: only hand-over envelopes, and so only the transcript deltas inside them, reached the rollout.

Not checked: for a brand-new thread with a voice-only call and no turn, exactly when the rollout file is first written to disk.

**3 (continued). Where, if anywhere, is a voice call's own transcript stored?** (read in the source)

Core keeps no separate file per call. In 0.167.0 the call's transcript lives in the thread it is attached to:
1. The thread's rollout file (the path hooks receive as `transcript_path`), as `realtime_item` lines and as `<realtime_delegation>` user messages.
2. A projection of those items in the SQLite file `thread_history_1.sqlite`, table `thread_realtime_items`, which serves the app server's history lists.
3. Live only, not stored: app-server notifications such as `thread/realtime/transcript/delta`, `thread/realtime/transcript/done` and `thread/realtime/itemAdded`.

Each item carries a `realtime_session_id` (the realtime provider's session id). That id and the client's `voice_session_id` identify the call; neither appears in any hook payload.

The official hooks page warns that "the transcript format isn't a stable interface for hooks and may change over time".

Unknown: whether the closed-source desktop app or OpenAI's servers keep another copy of the transcript or the audio. The official voice page says nothing about transcript or audio retention. Core has no code that writes audio to the rollout.

**4. What happens at the end of a voice call, normal or abrupt: does a session-end or stop hook fire, and under which session id?** (read in the source)

Ending a call fires no hook by itself, in either case.

What core does at the end of a call:
- It emits a `RealtimeConversationClosed` event (app-server notification `thread/realtime/closed`) with reason `requested` (the client stopped it), `transport_closed` (the connection ended) or `error`.
- On a paginated thread it writes a `realtime_session_closed` item to the rollout, with `outcome` `failed` if an error event was seen and `ended` otherwise.
- The close path does not abort a running agent turn. A hand-over turn that is still running finishes and fires its own Stop hook as usual.
- Remaining speech that was never handed over: only if the client started the call with `flushTranscriptTailOnSessionEnd` (default false; the 0.167.0 terminal UI does not set it). Since 0.162.0 (2026-10-08, PR #50531) the tail is saved into history as an envelope with `<source>transcript_tail_flush</source>`, with no model call and no hook; a test asserts that no model request is made at close and that the text first reaches the model on the next typed turn. From 0.145.0 to 0.160.0 the same tail was routed as a real turn, so on those releases it did fire UserPromptSubmit and Stop.

SessionEnd belongs to the thread, not the call. It fires when the thread is torn down: per the official page, when a still-open conversation is archived or deleted, on a normal Codex close, or after 30 idle minutes with no connected client. Its `session_id` is the thread's own id (a test asserts they are equal for a main thread), the same id every typed or handed-over turn on that thread reports, and its `reason` is always `other`. If a turn is running at teardown it is aborted as interrupted first, which fires Interrupt.

A hard crash of the Codex process is not covered by any source read; SessionEnd runs inside the shutdown routine, so it presumably does not fire then.

**5. Which Codex sessions fire a session-end hook without ever firing a session-start hook?** (read in the source)

Any main (non-subagent) thread that is loaded but never runs a regular turn. SessionStart is lazy: it is queued when the session is created and runs only at the start of the first regular turn. SessionEnd runs at teardown with no check that SessionStart ever ran. An app-server test starts two threads, runs no turn, shuts the server down (by end of input and by SIGTERM), and asserts one SessionEnd per thread.

In practice this covers:
- a thread opened or resumed only to look at it, then closed, archived, deleted or unloaded after 30 idle minutes;
- a thread that only had a voice call with no hand-over;
- a thread whose only activity was not a regular turn, such as a manual compaction (inferred from where SessionStart is run).

The same thread can also produce several SessionEnd and SessionStart events over its life (unload, then resume and a new turn with `source: "resume"`), all under one session id.

SessionEnd exists since 0.145.0 (2026-07-21, PR #33895). It does not accept MCP-tool handlers, always runs synchronously, and has a 1 second default timeout (3 at most).

**5 (continued). How do subagent, review, guardian and memory runs behave for session-start, stop and session-end hooks?** (inferred)

Decided by the session's source:

- Thread-spawned subagents: SubagentStart in place of SessionStart, SubagentStop in place of Stop, and never SessionEnd or Interrupt.
- Other subagent sources (review, compact, the subagent form of memory consolidation, and others): no SessionStart, no SubagentStart, no Stop, no SubagentStop, no SessionEnd, no Interrupt. Tests confirm this for a review-source thread (no Stop or SubagentStop, no SessionEnd).
- Guardian reviewers: started as an internal guardian source, but the session itself is given the subagent source `guardian`, so they fall in the group above. Some guardian forks are also ephemeral.
- Memory, phase 1 (extraction): a direct model call, not a session, so no hooks.
- Memory, phase 2 (the consolidation agent): a real thread with the internal source `memory_consolidation`, created ephemeral and with the plugins feature off. Its Stop and model-request hooks run only for managed and system hook sources, never user, project, session-flag or plugin hooks (the model-request part has a test). Reading the code, SessionStart, UserPromptSubmit, tool hooks and SessionEnd are not filtered by source for this thread, so user-level hooks would fire for it, under the thread's own session id, with a null `transcript_path` and the memories folder as `cwd`; plugin hooks would not load. No test asserts this, so treat it as likely, not certain.

What is not gated by source in the code: UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PreCompact and PostCompact have no session-source check. So in review-type sub-sessions they can still fire, without `agent_id`, even though no start or end event ever does. This too is a reading of the code with no test behind it.

**5 (continued). Which sessions have no transcript path in their hook payloads?** (read in the source)

`transcript_path` is JSON null in every hook payload of a session that has no local rollout file:
- ephemeral sessions (`ephemeral` in the session's config): ephemeral exec or app-server threads, the memory consolidation agent, ephemeral guardian forks. Such a session has no live thread at all;
- sessions on a thread store that is not the local one (remote or in-memory). A test asserts null for an in-memory store.

For a saved local thread the path is never null: before building the payload, core makes sure the rollout file exists on disk, even at SessionStart (test: the path exists when the hook runs). Before SessionEnd and Interrupt it also flushes the rollout, and tests show the SessionEnd hook can read the final turn from the file.

SessionEnd's payload is smaller than the others: only `session_id`, `transcript_path`, `cwd`, `hook_event_name` and `reason`; no `model`, `permission_mode` or `turn_id`.

**6. How do subagent threads appear to hooks: under their own session id, with an agent id field, with a parent id?** (read in the source)

Under the parent's session id, with an agent id, and with no parent-id field.

- `session_id` in every hook payload is the identity "shared by the root thread and all descendant threads", so a subagent's hooks report the root thread's session id, not their own thread id. The official page says: "Subagent hooks use the parent session id."
- `agent_id` is the subagent's own thread id and `agent_type` is its role (`default` when none was given). For a thread-spawned subagent they appear on SubagentStart, SubagentStop, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact and the model-request hooks. On a main thread they are absent; a test asserts the parent's UserPromptSubmit has neither field and the child's has both.
- There is no parent thread id, depth or agent path field in any payload.
- A spawned subagent fires SubagentStart (never SessionStart) at its first turn, whether it starts fresh or forks the parent's history, and SubagentStop (never Stop) when its turn ends. The matcher applies to `agent_type`.
- `transcript_path` differs by event. On SubagentStop it is the parent thread's rollout, and `agent_transcript_path` is the subagent's own. On the subagent's other events (SubagentStart, UserPromptSubmit, tool hooks) `transcript_path` is the subagent's own rollout.
- The subagent's first UserPromptSubmit carries the parent's spawn message as `prompt`.

SubagentStart and SubagentStop exist since at least 0.135.0 (2026-05-28).

**7. For comparison: does Claude Code have a voice or dictation mode, and does a dictated prompt arrive as an ordinary typed prompt?** (documented)

Claude Code documents voice dictation only: speech to text into the prompt box. Its documentation index lists no spoken-conversation mode with a separate front model.

- It is enabled with `/voice` (hold mode, default key Space, or tap mode). "Your speech is transcribed live into the prompt input, so you can mix voice and typing in the same message."
- In hold mode, by default, "Claude Code inserts the transcript and waits for you to press Enter". Tap mode, or `autoSubmit`, sends it automatically when the transcript has at least three words.
- Audio is streamed to Anthropic's servers for transcription and needs a Claude.ai account sign-in. The VS Code extension has it too.

So a dictated prompt arrives as an ordinary prompt: there is no envelope and no transcript of a front model. The UserPromptSubmit input documented for Claude Code is the common fields plus `prompt` (and `session_title` when set); it has no field for where the prompt came from. The same page notes that UserPromptSubmit also fires for scheduled tasks, background subagents reporting back, and messages from another session, again with no field that tells them apart.

Versions: the dictation page mentions builds up to v2.1.231 and the hooks page up to v2.1.314; neither shows a date. Read 2026-11-10.
