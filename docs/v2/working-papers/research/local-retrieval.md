# Retrieval that fits a single static binary with no daemon: how far past keyword matching can it go

Research notes, 2026-11-10. Every external fact carries its URL and the date of the source where it has one. "Fetched" means I read the page on 2026-11-10. Where I could not confirm something I say so. Confidence is marked H (read in a primary source), M (primary source but indirect, or two sources that are not strictly comparable), L (secondary source, or my own reasoning).

## 0. Where the system stands today (read from the local code, not from the web)

- Prompt recall (`internal/knowledgepage/recall.go`): the prompt's content tokens (runs of letters and digits, lowercased, 3+ characters, stoplist removed, at most 64) are matched as whole words against each knowledge row's title and statement. A row needs 2+ tokens, and either every content token of its title or 3+ prompt tokens. The score is a sum of normalized IDF, doubled for a title token, against a floor of 2.5; at most 3 rows are shown. The comment says the floor "was tuned on fixtures, not on real use".
- No stemming, no identifier splitting in recall (`ReadMax` is one token `readmax`), no aliases or expansion field, no phrase or proximity signal, no field beyond title and statement (the row's code paths are stored but not matched).
- The recall index is a TSV of at most 512 KiB read whole by the hook; the benchmark target is p95 under 50 ms for a prompt that recalls 3 facts.
- The inbox search index (`internal/searchindex`) is a hand-written segment index with BM25 (k1 1.2, b 0.75), camelCase and letter/digit splitting, and prefix match for tokens of 3+ characters. It serves search, not injection.
- The MCP server offers `eva_search`, `eva_show`, `eva_status`; there is a recall skill.

So the two tokenizers disagree, recall is exact-word only, and the strong model that writes each knowledge page contributes nothing to how the page is found. Those are the three cheapest gaps.

## 1. Lexical retrieval

### 1.1 BM25 is still the baseline to beat, and small models often do not beat it

- BEIR (Thakur et al., arXiv 2104.08663, Apr 2021, https://arxiv.org/abs/2104.08663): "BM25 is a robust baseline"; reranking and late-interaction models are best zero-shot "at high computational costs"; dense and sparse models are cheaper but "often underperform other approaches". (H)
- On 15 BEIR datasets (BMX paper, arXiv 2408.06643v2, 14 Aug 2024, table read from the PDF, https://arxiv.org/pdf/2408.06643): BM25S variants average 39.5 to 39.9 nDCG@10, the Baguetter BM25 40.4, all-MiniLM-L6-v2 41.95, bge-large-en-v1.5 53.60, mxbai-embed-large-v1 54.39. The BM25 variants (Robertson, ATIRE, BM25+, BM25L, Lucene) differ by under 0.5 points, so the choice of BM25 variant does not matter. (H)
- Consequence: a 22M-parameter transformer (MiniLM) is only about 2 points over BM25 on general text; the large gap opens only with 300M+ parameter encoders, which cannot run in a hook.

### 1.2 Code-aware tokenizing is the largest single lexical gain on technical text

- arXiv 2605.18561 (Radha and Goktas, 18 May 2026, https://arxiv.org/abs/2605.18561 and https://arxiv.org/html/2605.18561): on CoIR CodeSearchNet-Go (50K docs) BM25 with a generic tokenizer scores nDCG@10 0.309; an identifier-aware tokenizer that emits whole identifiers plus their sub-tokens scores 0.563 (+82%). Java +27.8%, Ruby +22.5%, Python +0.3% (whitespace-only tokenizing was best for Python, +17.5%). The paper's own IDF fix (q-log) adds +71.9% under the generic tokenizer but only +0.2% once the tokenizer is identifier-aware: "the tokenizer change captures nearly all of the improvement". On BEIR text the change is within noise (NFCorpus -0.002, SciFact -0.006, ArguAna -0.001). (H)
- Why: a generic analyzer keeps `handleWebSocketUpgrade` as one rare token; documents that share several common tokens outrank the right one (same source). (H)
- Semble (MinishLab, 2026, https://github.com/MinishLab/semble, fetched): query tokens are stemmed and matched against identifier stems, so "parse config" boosts `parseConfig`, `ConfigParser` and `config_parser`. (H)
- A pure-Go example exists: aikit's default BM25 tokenizer splits camelCase, PascalCase, ACRONYM boundaries and digits and keeps the lowercased whole run (https://github.com/townsendmerino/aikit, v1.76.0 of 2026-10-27, fetched). (H that it exists; the project has 6 stars, so it is a reference, not a dependency candidate.)

### 1.3 BM25F and field weighting

- Sourcegraph, "Keeping it boring (and relevant) with BM25F" (Julie Tibshirani, 4 Apr 2025, https://sourcegraph.com/blog/keeping-it-boring-and-relevant-with-bm25f): "roughly 20% improvement across all key metrics" on internal evaluations (data not published). Fields are file content, symbol definitions and file names; a match in a file name or a symbol adds 5 to the term frequency, content counts 1; the ranking "isn't very sensitive to the exact value". They rejected summing separate per-field BM25 scores (weights 2.5 and 5) because it over-rewards documents that match in several fields and breaks the probabilistic model. They chose BM25 over embeddings and learned ranking because it is simple, interpretable and zero-shot (COBOL, internal languages), and because "users and LLM agents still need lexical matching". (H for the claims, M for the size of the gain since the evaluation is internal.)
- SQLite FTS5 implements the weaker form: `bm25(tbl, w1, w2, ...)` with per-column weights, k1 1.2 and b 0.75 hard-coded (https://www.sqlite.org/fts5.html, fetched). (H)
- Lesson for the knowledge row: combine fields inside the term-frequency (true BM25F), not by adding per-field scores. Today's "title counts twice" is a per-field multiplier on IDF, the pattern Sourcegraph moved away from.

### 1.4 Stemming, phrase and proximity

- Stemming: I found no clean recent ablation that isolates stemming on short technical text. FTS5 ships a Porter wrapper (https://www.sqlite.org/fts5.html); the NanoBEIR BM25 baseline that the static-embedding work compares against uses bm25s with PyStemmer (https://huggingface.co/sentence-transformers/static-retrieval-mrl-en-v1, fetched). A zero-dependency pure-Go Snowball exists: github.com/kljensen/snowball v0.10.0 (2024-08-13), go.mod has no requirements (https://proxy.golang.org/github.com/kljensen/snowball/@latest, fetched). (H for availability, L for the size of the gain: must be measured in-house.)
- Phrase and proximity: FTS5 has phrase and `NEAR(a b, 10)` queries (same page). For records capped at a title and a 300-character statement the whole record is one sentence, so proximity carries little extra signal (my reasoning, L). I did not find measured evidence for proximity on very short documents.
- Ranking signals beat a second retriever (Semble ablation, https://minish.ai/packages/semble/benchmarks/, fetched, about 1,250 queries, 63 repositories, 19 languages, labels by an LLM judge): raw BM25 nDCG@10 0.675, raw static embedding 0.650; with Semble's ranking stack (identifier-stem match, definition boost, file coherence, penalties for tests and shims, more lexical weight for symbol-like queries) BM25 reaches 0.834 and the embedding 0.821; the hybrid reaches 0.854. The domain-aware ranking added about +0.16; adding the second retriever added +0.02. (H for the numbers; they are the vendor's own benchmark.)

### 1.5 The prompt is a verbose query

- Bendersky and Croft (SIGIR 2008) and follow-ups: search engines "do not, in general, perform well with longer, more verbose queries"; identifying key concepts, or removing "stop structure", significantly improves effectiveness (survey: https://www.microsoft.com/en-us/research/wp-content/uploads/2015/03/Information_Retrieval_With_Verbose_Queries.pdf; I read search summaries only). (M)
- Consequence: a chat prompt needs query reduction before matching: keep identifiers, paths, quoted strings, error codes and rare words; the present stoplist plus IDF is a weak version of this.

## 2. Write-time expansion by a model

### 2.1 doc2query and its filter

- Doc2query (Nogueira et al., arXiv 1904.08375, Apr 2019, https://arxiv.org/abs/1904.08375): predict the queries a document answers and append them; retrieval alone "approach[es] the effectiveness of more computationally expensive neural re-rankers but [is] much faster". (H)
- docTTTTTquery (Nogueira and Lin, 2019, table read from the PDF, https://cs.uwaterloo.ca/~jimmylin/publications/Nogueira_Lin_2019_docTTTTTquery-v2.pdf): MS MARCO passage dev MRR@10: BM25 0.184; doc2query 0.218; docTTTTTquery with 5 generated queries 0.259, 10 queries 0.265, 40 queries 0.277, 80 queries 0.278; BM25 + BERT-large reranking 0.375. Query latency 55 ms for BM25, 58 to 66 ms expanded, 3,500 ms with the reranker. Recall@1000 rises from 0.853 to 0.947. Five queries per passage give most of the gain. (H)
- Doc2Query-- (Gospodinov, MacAvaney, Macdonald, ECIR 2023, arXiv 2301.03266, https://arxiv.org/abs/2301.03266): generated queries hallucinate; removing the poor ones with a relevance model improves effectiveness by up to 16%, cuts mean query time by 23% and index size by 33%. (H)

### 2.2 Evidence from memory benchmarks: expand the key, in the same record

- LongMemEval (Wu et al., ICLR 2025, arXiv 2410.10813v2, https://arxiv.org/html/2410.10813v2): appending extracted facts to the key (K = V + fact) gives +9.4% recall@k and +5.4% answer accuracy on average. Table 3 (LongMemEval-M, Stella retriever): round values R@5 0.582 to 0.644, session values R@5 0.706 to 0.732 and R@10 0.783 to 0.862. Replacing the value by the extraction hurts: K = fact 0.530, K = keyphrase 0.282 (round R@5); K = V + keyphrase also hurts for rounds (0.478). (H)
- Same paper, appendix E.2: BM25 is lower than dense retrievers here (session R@5 0.634 against Contriever 0.723 and Stella 0.720), and fact expansion lifts BM25 to 0.683. (H)
- Same paper, appendix E.3: "rank merging has much lower performance than key merging": separate index entries for the extractions, merged by rank, give round R@5 0.478 against 0.644 for appending them to the same key; answer accuracy 0.558 against 0.657. (H)
- Same paper, section 5.4: time-aware query expansion (a strong LLM extracts a time range and the search is restricted to it) improves recall on temporal questions by 6.8% to 11.3%; a weak model (Llama 3.1 8B) does not get the gain. (H)

### 2.3 Contextual retrieval

- Anthropic, "Contextual Retrieval" (19 Sep 2024, https://www.anthropic.com/engineering/contextual-retrieval): a model writes 50 to 100 tokens of context for each chunk, prepended before embedding and before the BM25 index. Top-20 retrieval failure rate: 5.7% baseline; 3.7% with contextual embeddings (-35%); 2.9% with contextual embeddings plus contextual BM25 (-49%); 1.9% with reranking (-67%). BM25 is credited for exact identifiers (the example is error code "TS-999"). For a knowledge base under 200,000 tokens the post says to put the whole thing in the prompt and skip retrieval. (H)

### 2.4 Learned sparse expansion: what document-side work buys against embeddings

- OpenSearch inference-free sparse encoders (model card, paper of 21 Apr 2025, https://huggingface.co/opensearch-project/opensearch-neural-sparse-encoding-doc-v3-distill, fetched): documents are expanded by a model at index time; queries need only "a tokenizer and a weight look-up table" (IDF). BEIR average nDCG@10: doc-v1 0.490, doc-v2-distill 0.504, doc-v3-distill 0.517, doc-v3-gte 0.546, against 0.524 and 0.528 for the same family's models that also run a model on the query. (H)
- Read against section 1.1 (BM25 about 0.40, bge-large 0.536 on a slightly different BEIR subset): doing all the semantic work on the document side, with a plain weighted-token query, closes most or all of the gap to a strong dense bi-encoder. (M: the dataset subsets differ, 13 against 15.)
- These encoders are 67M to 133M-parameter transformers, so they do not fit "no local model". The host's own model writing the expansion is the available substitute; it is less systematic but far stronger at knowing what the fact is about.

### 2.5 When expansion fails

- Weller et al., "When do Generative Query and Document Expansions Fail?" (EACL 2024, arXiv 2309.08541, https://arxiv.org/abs/2309.08541): across 11 expansion techniques, 12 datasets and 24 retrievers there is "a strong negative correlation between retriever strength and the gains from expansion": expansion helps weak retrievers and hurts strong ones; expansions add useful recall but also noise that creates false positives at the top. (H)
- Reading for this system: the retriever here is the weak kind (lexical, short records), which is where expansion helps. The false-positive warning applies directly to injection, where precision is what matters.
- HyPE (Vake, Vičič, Tošić, IEEE Access 2025): precompute hypothetical prompts per chunk at index time and match the query against those; the authors report up to +42 points context precision and +45 points claim recall. I saw only search summaries and could not confirm the arXiv id. (L)
- A 2023 study (arXiv 2309.17078) is reported to lift BM25 from .246 to .292 on short documents with five LLM-generated queries each; search summary only. (L)

## 3. Static embeddings (no model at query time)

### 3.1 What they are and what they cost

- Model2Vec / potion: a vocabulary is passed through a sentence transformer, reduced with PCA, weighted (SIF/Zipf); inference is a token lookup and a mean (https://github.com/MinishLab/model2vec, fetched). The base package's "only major dependency is numpy"; the best general model is about 30 MB on disk (potion-base-8M), the smallest about 8 MB. (H)
- potion-base-8M: 7.56M parameters, F32, teacher bge-base-en-v1.5, MIT (https://huggingface.co/minishlab/potion-base-8M, fetched). potion-retrieval-32M: 32.3M parameters, F32, trained with Matryoshka dimensions 32 to 512, MIT (https://huggingface.co/minishlab/potion-retrieval-32M, fetched). potion-code-16M-v2: 16.2M parameters, 256 dimensions, F16, vocabulary about 63,500 with about 43k code tokens added, teacher CodeRankEmbed, MIT (https://huggingface.co/minishlab/potion-code-16M-v2, fetched). (H)
- Model2Vec documents float16 and int8 embeddings (2x to 4x smaller "with little quality loss") and vocabulary quantization; no numbers given (https://minish.ai/packages/model2vec/introduction/, fetched). (M)
- sentence-transformers static-retrieval-mrl-en-v1 (blog of 15 Jan 2025, https://huggingface.co/blog/static-embeddings): an `EmbeddingBag(30522, 1024)` over the bert-base-uncased tokenizer; 107,419 sentences per second on CPU against 270 for all-mpnet-base-v2 (397x). Matryoshka truncation, NanoBEIR nDCG@10: 1024d 0.5031, 512d 0.4957, 256d 0.4819, 128d 0.4622, 64d 0.4176, 32d 0.3532 (https://huggingface.co/sentence-transformers/static-retrieval-mrl-en-v1). (H)
- WordLlama: 16 MB default model at 256 dimensions, numpy-only inference, MIT, supports binary embeddings with Hamming distance; no MTEB retrieval figure is published, and its CQADupstack score is 24.12 at 256d against 41.32 for all-MiniLM-L6-v2 (https://github.com/dleemiller/WordLlama, fetched). (H) It is the weakest documented option for retrieval.

### 3.2 Measured quality against BM25 and against transformers

General English text:
- NanoBEIR nDCG@10 (HF blog, 15 Jan 2025): static-retrieval-mrl-en-v1 0.5032, BM25 0.4518, all-mpnet-base-v2 0.5757. The static model keeps 87.4% of mpnet and is "the only static model" that beats BM25 there. (H)
- Full MTEB retrieval (https://minish.ai/packages/model2vec/results/, fetched): all-MiniLM-L6-v2 42.92, potion-retrieval-32M 35.06, static-retrieval-mrl-en-v1 34.95, potion-base-32M 32.67, potion-base-8M 31.11, GloVe 300d 21.80. (H)
- Putting the two together: on full-size BEIR-style corpora the best static models (about 35) sit below BM25 (about 40, section 1.1); on the small NanoBEIR subsets one static model sits above BM25. The static-versus-BM25 order depends on the corpus. (M: different dataset subsets.)

Code and technical text:
- CoIR nDCG@10 (potion-code-16M-v2 card): CodeRankEmbed (137M transformer) 59.14; hybrid potion-code-16M-v2 + BM25 43.36; BM25 42.31; potion-code-16M-v2 39.08; potion-retrieval-32M 32.10. Per task BM25 wins where the query shares words with the answer (StackOverflow 70.26 against 59.57; CodeFeedback-ST 68.15 against 53.22) and the static model wins where it does not (Text2SQL 44.07 against 24.94; CosQA 24.36 against 18.75). (H)
- Semble by query category, with the ranking stack (https://minish.ai/packages/semble/benchmarks/): BM25 / static / hybrid: architecture 0.770 / 0.757 / 0.802; semantic 0.819 / 0.808 / 0.846; symbol 0.957 / 0.943 / 0.958. The embedding adds about 3 points on vague queries and nothing on symbol lookups. Query p50 0.91 ms; index 306 ms for an average repository. (H)
- I found no measurement of static embeddings on short agent-memory statements with chat prompts as queries. (gap)

### 3.3 Can it run in pure Go

- No official Go port. The official ports are Python and Rust (model2vec-rs, which uses the Rust `tokenizers` crate; https://docs.rs/model2vec-rs, fetched via search). Two searches found no maintained Go port from the authors. (M)
- A third-party pure-Go implementation exists: aikit loads Model2Vec models (the vocabulary-quantized potion-code-16M format and the plain format), has a WordPiece tokenizer and a safetensors reader, checks parity against Python through golden fixtures, embeds in "microseconds per text", has an mmap loader, and depends only on the standard library plus golang.org/x/text and x/sys; a static binary with its ann, bm25, fuse and embed packages is about 1.8 MB (https://github.com/townsendmerino/aikit and https://pkg.go.dev/github.com/townsendmerino/aikit, v1.76.0, 2026-10-27; go.mod read from https://proxy.golang.org). It reports potion-retrieval-32M at nDCG@10 0.638 on BEIR SciFact (all-MiniLM-L6-v2 scores 64.51 there per the BMX table). (H that it exists and what it claims; the repository has 6 stars and one author, so treat it as proof of feasibility and a reference to read, not as a dependency.)
- What a home-grown port needs (my reading of the format, L): a safetensors reader (an 8-byte little-endian header length, a JSON header, raw tensor bytes; https://huggingface.co/docs/safetensors/index, where the format diagram did not render in my fetch), a BERT-style normalizer and WordPiece tokenizer, a lookup and a weighted mean. Parsing a 30k to 60k entry `tokenizer.json` on every hook start would eat the budget, so the vocabulary should be converted once to a binary, mmap-friendly table.
- Transformer embeddings in pure Go are too slow for a hook: goformer (v0.1.0, 8 Mar 2026, https://pkg.go.dev/github.com/MichaelAyles/goformer) takes 154 ms for a 5-token text and 1.1 s for 40 tokens with bge-small on an Apple M1, 91 ms to load, about 261 MB allocated; aikit reports about 46 ms per short text for all-MiniLM-L6-v2 single-threaded and about 360 ms at 256 tokens. (H as self-reported.)
- NIFE (Stéphan Tulkens, https://github.com/stephantul/pynife, search summary): a static query encoder aligned with a large transformer's document embeddings, so documents are embedded by the big model at write time and queries by a lookup. It needs a local transformer or an embedding API at write time. (L)

## 4. Small vector search without a database

- Brute force is enough at this scale. chromem-go (pure Go, zero third-party dependencies, exhaustive cosine; README benchmark of 2024-03-17 on a 2020 Intel i5-1135G7 laptop, https://github.com/philippgille/chromem-go): 1,000 documents 0.52 ms, 5,000 documents 2.1 ms, 25,000 about 10 ms, 100,000 about 39.5 ms. v0.7.0 is from 2024-09-01 and its go.mod has no requirements. (H)
- sqlite-vec v0.1.0 (Alex Garcia, 1 Aug 2024, https://alexgarcia.xyz/blog/2024/sqlite-vec-stable-release/index.html): brute force only; at 100K vectors every float dimension from 192 to 1024 stays under 75 ms and 3072-dimension bit vectors take 11 ms; the author puts the practical limit for latency-sensitive use "in the 100's of thousands" of vectors. (H)
- Binary and scalar quantization (Hugging Face blog, 2024, https://huggingface.co/blog/embedding-quantization): binary is 32x smaller and retains about 92.5% without and up to about 96% with rescoring for mxbai-embed-large; int8 is 4x smaller at about 97% to 99%; rescoring used 4x oversampling. Retention is model-dependent: all-MiniLM-L6-v2 (384d) keeps 93.79% binary and 90.79% int8; e5-base-v2 keeps 74.77% binary. No static model was tested. (H)
- Arithmetic for this corpus (L): 5,000 vectors of 256 dimensions are 5.1 MB as float32, 1.3 MB as int8, 160 KB as bits. At that size quantization is about file size and page-cache cost, not search time.
- File format (L, my recommendation): one flat little-endian file: magic, version, model fingerprint, dimension, count, dtype, then the row ids, then the matrix; read whole or mmap; rebuilt from the Markdown pages like the present recall index, never committed. chromem-go's one-gob-file-per-document layout is the pattern to avoid for a hook.

## 5. Embedded stores against a hand-written index

- modernc.org/sqlite (pure Go, transpiled C): v1.62.0 of 2026-11-07; platforms include darwin amd64/arm64 and linux; ships sqlite-vec in its `vec` package; measured in Sept 2026 at 1.3x to 2.0x the CPU time of C SQLite on CPU-bound queries; the docs warn that the libc version in your go.mod must match theirs, "a fragile dependency" (https://pkg.go.dev/modernc.org/sqlite, fetched). Its go.mod requires 5 direct and 6 indirect modules (https://proxy.golang.org/modernc.org/sqlite/@v/v1.62.0.mod). I could not confirm from the page whether FTS5 is compiled in by default, nor the binary-size cost. (H for what is listed.)
- ncruces/go-sqlite3: cgo-free; wraps a Wasm build of SQLite translated to Go with wasm2go (it moved off the wazero runtime in March 2026); v0.37.0 of 2026-11-07; "memory usage is higher than alternatives because each connection runs in a Wasm sandbox"; FTS5 was recently split into its own module (https://github.com/ncruces/go-sqlite3, fetched; go.mod from the Go proxy). Start-up cost in a short-lived CLI is not documented. (H for what is listed.)
- FTS5 gives porter and trigram tokenizers, per-column BM25 weights, phrase, NEAR, prefix indexes (https://www.sqlite.org/fts5.html). It cannot emit identifier sub-tokens without a custom tokenizer, and k1 and b are fixed. (H)
- bleve v2.6.3 (2026-11-04): go.mod lists 28 direct requirements including go-faiss, bbolt, protobuf and cobra (https://proxy.golang.org/github.com/blevesearch/bleve/v2/@latest). Out of proportion for a binary with two dependencies. (H)
- Judgment (L): the knowledge corpus is a few thousand rows under 512 KiB; a linear scan is about a millisecond, so no index structure is needed for it at all. The inbox already has a purpose-built segment index. A SQLite dependency would buy query convenience and transactions, not recall quality, and costs the dependency rule, binary size, a cold open in every hook process and a second source of truth to keep honest. Hand-written stays right for the hook path.

## 6. Hybrid fusion

- RRF (Cormack, Clarke, Büttcher, SIGIR 2009, read from the PDF, http://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf): score(d) = sum over rankings of 1 / (k + rank(d)), k = 60 "near-optimal, but ... not critical"; RRF beat Condorcet, CombMNZ and the best single system by 4% to 5% on average over TREC runs. (H)
- Measured gains for lexical + static: CoIR 42.31 to 43.36 (+1.05 points; potion-code-16M-v2 card, https://huggingface.co/minishlab/potion-code-16M-v2; the v1 card, https://huggingface.co/minishlab/potion-code-16M, describes the hybrid as min-max score normalization with equal weights, alpha 0.5); Semble 0.834 to 0.854 with RRF (section 1.4). Small, consistent, concentrated on vague queries. (H)
- Contextual retrieval: adding contextual BM25 to contextual embeddings moved the failure rate from 3.7% to 2.9% (section 2.3). (H)
- When it does not help: LongMemEval found merging at index time (one enriched key) clearly better than merging ranked lists (section 2.2). A weak ranker gets an equal vote in RRF and can pull a strong one down; I found this stated only in practitioner posts, not in a paper I could verify. (L)
- Reading: fusion is the last few points, not the first. It is worth having only once a second retriever exists and an evaluation shows the two fail on different prompts.

## 7. Read-time intelligence without a hook-time model

### 7.1 What the hosts allow at hook time (docs fetched 2026-11-10)

- Claude Code (https://code.claude.com/docs/en/hooks): `additionalContext` on UserPromptSubmit and SessionStart is wrapped in a system reminder; each string is capped at 10,000 characters, beyond which Claude gets a file path and a 2,000-character preview; the default timeout on UserPromptSubmit is 30 s; the page says to phrase context as factual statements because text framed as out-of-band system commands can trigger prompt-injection defenses. PostToolUse can also return `additionalContext`. (H)
- Claude Code hook types: `command`, `http`, `mcp_tool`, `prompt`, `agent`. `prompt` hooks call a model but return only `ok` / `reason` (allow or block); they cannot add context. `agent` hooks are marked experimental. (H)
- `mcp_tool` hooks call a tool on a configured MCP server (a plugin's server is addressed as `plugin:<plugin>:<server>`); the tool's text output "is parsed like command-hook stdout". They are skipped on SessionStart at launch because servers are not connected yet. The page does not say outright that such a result can carry `additionalContext`; by the parsing rule it should. (H for the mechanism, M for the context path.)
- Codex (https://learn.chatgpt.com/docs/hooks, redirected from developers.openai.com/codex/hooks): events include SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop; plain stdout or `hookSpecificOutput.additionalContext` on UserPromptSubmit becomes developer context; "`command` and `mcp_tool` handlers are supported. `prompt` and `agent` handlers are parsed but skipped"; each model-visible hook output is limited to roughly 2,500 tokens by default. (H as fetched.)
- So there is no portable way to run a model inside a hook, but both hosts let a hook call a tool on an MCP server that is already running for the session. That is a resident process the host starts and stops; the product still installs no daemon.

### 7.2 Agent-led retrieval works, when the agent chooses to do it

- Letta, "Benchmarking AI Agent Memory: Is a Filesystem All You Need?" (12 Aug 2025, https://www.letta.com/blog/benchmarking-ai-agent-memory): an agent on GPT-4o mini with `grep`, `search_files`, `open` and `close` over the conversation history stored in files scored 74.0% on LoCoMo, above Mem0's reported 68.5% for its graph variant. Their explanation: agents are trained on file tools, rewrite the question into better queries and keep searching; "whether an agent 'remembers' depends on whether it knows when and how to use its retrieval tools". Vendor-reported. (H for the claim.)
- Claude Code's team is reported to have dropped an early "RAG + local vector db" design for agentic search with glob and grep; the quotes come from secondary write-ups of a Latent Space episode (7 May 2025) and an X post, which I could not read in the original. (L)
- Cursor, "Improving agent with semantic search" (6 Nov 2025, https://cursor.com/blog/semsearch): adding semantic search to grep raised answer accuracy by 12.5% on average (6.5% to 23.5% by model); in an A/B test code retention rose 0.3% overall and 2.6% in codebases of 1,000+ files; both tools together are best. (H)
- Turbopuffer talk at AI Engineer Europe 2026 (https://www.ai.engineer/talks/zKk7sDMGDEQ-benchmarking-semantic-code-retrieval-on-claude): on 50 tasks, semantic search plus windowed reads raised file precision from about 65% to about 87%, while stock Claude Code kept the best file recall; "Claude Code didn't reliably choose the semantic tool". (M: small sample, talk summary.)
- Anthropic, "Effective context engineering for AI agents" (29 Sep 2025, https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents): prefer lightweight references loaded just in time; Claude Code is the hybrid model (CLAUDE.md up front, glob and grep on demand); sub-agents explore in their own windows and return 1,000 to 2,000-token summaries; find "the smallest set of high-signal tokens". (H)

### 7.3 The agent often does not look: passive context beats on-demand retrieval

- Vercel, "AGENTS.md outperforms skills in our agent evals" (27 Jan 2026, https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals): pass rates: no docs 53%; a skill 53%; the skill plus explicit instructions to use it 79%; an 8 KB compressed docs index in AGENTS.md 100%. "In 56% of eval cases, the skill was never invoked". Reasons given: no decision point, always available, no ordering problem. (H)
- Claude Code auto memory (https://code.claude.com/docs/en/memory, fetched): the first 200 lines or 25 KB of `MEMORY.md` load in every session; topic files are not loaded and Claude "reads them on demand using its standard file tools". No embedding or search layer: an always-loaded index plus file reads. Path-scoped rules (`paths:` frontmatter) load only when Claude works with matching files. (H)
- Anthropic's memory tool (https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool, fetched; tool type `memory_20250818`, status stable): a directory of files the model views and edits; the API adds "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" to the system prompt. Retrieval is the model listing and reading files. (H)
- Codex memories (https://learn.chatgpt.com/docs/customization/memories, fetched): generated in the background from idle chats into files under `~/.codex`; `memories.use_memories` controls injection into later sessions; the page does not say how they are selected. (H for what is stated; mechanism unconfirmed.)
- Mastra observational memory (9 Feb 2026, https://mastra.ai/research/observational-memory): no per-turn retrieval at all; background agents compress history into a dated observation log kept in a stable, cacheable prefix of about 30k tokens; 94.87% on LongMemEval-S with gpt-5-mini, 84.23% with gpt-4o against 80.05% for their own RAG baseline and 60.20% for full context. Vendor-reported. (H for the claim.)
- Tool discoverability in Claude Code (https://code.claude.com/docs/en/mcp, fetched): tool search is on by default, so "only tool names and server instructions load at session start"; server instructions are cut at 4,096 characters; a server can mark a tool `anthropic/alwaysLoad`. Skill descriptions are cut at 1,536 characters (https://code.claude.com/docs/en/skills, fetched). So whether the agent recalls depends on a few hundred characters of trigger text. (H)

## 8. When to inject

### 8.1 Wrong context costs more than no context

- Chroma, "Context Rot" (Hong, Troynikov, Huber, 14 Jul 2025, https://www.trychroma.com/research/context-rot), 18 models: one distractor (related to the topic but not the answer) lowers accuracy against the needle-only baseline, four lower it further, and distractors differ in harm; on LongMemEval every model did markedly better with a focused prompt of about 300 tokens than with the full 113k tokens. (H)
- Cuconasu et al., "The Power of Noise" (arXiv 2401.14887, Jan 2024, https://arxiv.org/abs/2401.14887): retrieved passages that score high but do not hold the answer hurt the model, while random documents do not (they even helped, by up to 35%). The damaging case is the near miss, which is exactly what a keyword recall with a low floor produces. (H)
- Xiong et al., "How Memory Management Impacts LLM Agents" (arXiv 2505.16067, May 2025, https://arxiv.org/abs/2505.16067; abstract-level reading): agents show "experience-following": when a retrieved memory resembles the task, the output follows it; memories that look similar but do not fit degrade performance and errors propagate; selective addition with evaluator feedback gained about 10 points on average. (M)

### 8.2 Abstaining is harder than selecting, and lexical scores are poor at it

- "Selection Is Retrieval, Abstention Is Not" (Lee, arXiv 2609.18672, 16 Sep 2026, https://arxiv.org/abs/2609.18672), 600 requests over a catalog of 70 actions: character-3-gram BM25 picks the right action for 162 of 164 lexically matched requests but 85 of 166 paraphrases; restricting candidates to seven raises paraphrase accuracy to 0.825; classifiers over BM25 score features tell in-catalog from out-of-catalog requests with AUC at most 0.697, a frozen multilingual-e5-base reaches 0.806. "Abstention, not selection, is where a neural component is required." One preprint. (M)
- Query-performance predictors computed from scores (clarity, NQC) depend heavily on the collection (2025 study, search summary only). (L)
- Reading: a raw score floor will not generalize from fixtures to real prompts. Gates built from structure hold up better: an exact rare key (path, identifier, error code, name), full coverage of a title, the project scope, a margin over the runner-up.

### 8.3 Host limits that shape injection

- 10,000 characters per context string in Claude Code; about 2,500 tokens per hook output in Codex (section 7.1). Statements should read as facts, not commands (Claude Code hooks page). (H)

## 9. A ranked ladder, cheapest first

Each step says what to do, what it costs, and the evidence. Steps 0 to 4 need no new dependency, no model file and no change to "no daemon".

0. Build the evaluation before changing recall. A labelled set of real prompts (redacted), each with the knowledge rows that should fire and, as important, prompts where nothing should fire. Report injection precision, recall, and the silent rate; split by lexical match against paraphrase. Evidence: the present floor is tuned on fixtures; abstention is the hard half and lexical score features reach only about 0.70 AUC (8.2); the Vercel result came from an eval, not intuition (7.3). Cost: days, plus the developer's own inbox as raw material. Without it none of the steps below can be judged.

1. One tokenizer and a real BM25F for recall. Share the identifier-aware tokenizer between search and recall (whole identifier plus camelCase, snake_case, digit and path-segment parts); add a light English stemmer for prose tokens only; score title, statement, expansion field and code paths as BM25F fields combined in the term frequency; reduce the prompt to its informative terms. Evidence: identifier-aware tokenizing +82% / +28% / +23% BM25 nDCG on Go / Java / Ruby code search and neutral on prose (1.2); BM25F about +20% at Sourcegraph (1.3); domain-aware ranking signals +0.16 nDCG in Semble, eight times what a second retriever added (1.4). Cost: a few hundred lines of Go, microseconds at run time, no dependency (a Snowball stemmer can be written or vendored without a module).

2. Make the write-time model write the retrieval keys. When the update creates or supersedes a knowledge page, it also writes, into the page's frontmatter and the recall index: 3 to 5 prompts or situations in which this knowledge should come up, aliases and synonyms for its terms, and the identifiers, commands and paths it concerns. Index them as a separate lower-weight field of the same record; ground-check them against the cited entries and drop the ones that add words the source does not support. Evidence: docTTTTTquery lifts BM25 MRR@10 from 0.184 to 0.277 at no query cost, with five queries giving most of it (2.1); filtering hallucinated expansions is worth up to another 16% (2.1); fact-augmented keys +9.4% recall and +5.4% accuracy, and merged keys beat merged rankings 0.644 to 0.478 (2.2); contextual BM25 (2.3); document-side-only learned expansion matches models that also encode the query (2.4). Cost: more output tokens per update pass, a schema change to the page and the index, and a re-pass over existing pages. Risk: expansion noise creates false positives (2.5), so expansions may widen the candidate list while the injection gate keeps demanding a match in the title or statement or an exact key.

3. Scope and exact keys before fuzzy matching. Fire recall from what the agent touches, not only from what the user types: a PostToolUse hook on file reads and edits looks the path up among the rows' code paths; an error string or identifier in tool output is looked up exactly. Keep project scope as a hard filter. Evidence: restricting candidates raised paraphrase accuracy from 51% to 82.5% (8.2); Claude Code's own path-scoped rules load on matching files (7.3); exact identifiers are where BM25 is strongest (1.2, 2.3). Cost: one more hook path with the same latency rules; per-session de-duplication so a row is said once.

4. Give the model a small always-present map and let it choose. At session start, inside the brief's budget, list the project's knowledge as one line each (title, kind, id), ranked by scope, recency and past use, and tier the per-prompt recall: strong match, inject the statement; medium match, inject a one-line pointer with its id; weak match, stay silent. Put the "when to search" rule in the MCP server instructions and mark the search tool always-loaded. Evidence: an 8 KB always-present index scored 100% where a skill scored 53% to 79% and went unused 56% of the time (7.3); Claude Code's own memory is an always-loaded 200-line index plus on-demand reads (7.3); a stable log with no retrieval reached 94.87% on LongMemEval (7.3); under 200k tokens Anthropic says to skip retrieval (2.3). Cost: a few hundred to a couple of thousand tokens per session; the map must be capped and ranked as the wiki grows.

5. Agent-side deep recall. A recall subagent (or a forked skill) that runs multi-step search over the wiki and the inbox with date and path filters and returns a digest of 1,000 to 2,000 tokens, used when the user asks about history or the main agent hits an unknown. Evidence: a file-tool agent beat a dedicated memory library on LoCoMo (7.2); time-aware filtering by a strong model +7% to +11% on temporal questions (2.2); sub-agent digests keep the main context clean (7.2). Cost: seconds and tokens per use, so on demand only; Codex and Claude Code differ in how subagents are declared.

6. A warm process without a daemon. Move per-prompt recall behind an `mcp_tool` hook that calls the plugin's own MCP server, which the host already keeps running for the session, with the command hook as the fallback (SessionStart at launch cannot use it). The server holds the parsed index, and later a model, in memory. Evidence: both hosts document `mcp_tool` hook handlers (7.1). Cost: a second code path to test on both hosts; behaviour when the server is slow or absent must stay fail-closed. Unverified live: that the tool result is accepted as `additionalContext` on UserPromptSubmit in both hosts.

7. Static embeddings as a second signal, only if the evaluation still shows a paraphrase gap after steps 1 to 4. Embed each knowledge record (statement plus expansions) at write time with a static model, store int8 vectors in a flat cache file, embed the prompt by lookup in the hook, brute-force the few thousand rows, and fuse with the lexical list (weighted RRF). Evidence for: +1 point on CoIR, +0.02 nDCG on Semble, about +3 points on vague queries and none on symbol lookups (3.2, 6); pure-Go feasibility shown by a third party at about 1.8 MB of code (3.3); brute force over 5,000 vectors is about 2 ms in pure Go (4). Evidence against: static models score about 35 on MTEB retrieval against about 40 for BM25 and 43 for MiniLM (3.2); abstention, not ranking, is where an encoder helped most in the one study that measured it (8.2), which argues for using the embedding as a gate feature as much as a ranker. Cost: an 8 to 30 MB model file to ship or download and to version, a WordPiece tokenizer and safetensors reader to own, re-embedding when the model changes, and a new cache to rebuild. No measurement exists for this kind of corpus, so this step must be earned by step 0's numbers.

8. Heavier models, only behind step 6. With a resident server a 32M static model, or a small transformer used as reranker or abstention gate, loads once per session rather than once per prompt. Pure-Go transformer inference is 46 to 154 ms per short text today (3.3), so this is a watch item, not a plan.

Not on the ladder: a vector database, an embedded SQL store for the hook path (5), a local LLM, hook-time network calls, HyDE-style query expansion at hook time (it needs a model per prompt).

## 10. Questions I could not settle

- How large the stemming gain is on short technical statements; no clean ablation found.
- Whether static embeddings help at all on chat-prompt-to-knowledge-statement matching; no published measurement; needs the in-house evaluation.
- Whether an `mcp_tool` hook result is honoured as `additionalContext` on UserPromptSubmit in both hosts, how long the host waits for the server, and the added latency compared with a spawned command.
- The binary-size and cold-open cost of modernc.org/sqlite or ncruces/go-sqlite3 in a short-lived process, and whether FTS5 is in modernc's default build.
- How Codex selects which memories to inject.
- The Claude Code team's own evidence for agentic search over a local vector index: only secondary quotes found.
- Whether binary or int8 quantization holds up for 256-dimension static models; the published retention numbers are for transformer embeddings.
- What rate of wrong injections real users tolerate before they notice; no study found for coding agents.

## Fact check

Checked 2026-11-10 by a second reader, against the primary sources (raw pages, the Go module proxy, the PDFs), trying to prove each fact wrong. 25 of the 30 facts were read at source; F11, F16, F18, F20 and F23 were not checked. Verdicts: confirmed, partly (what is off), refuted, could-not-check.

### Partly right: correct these before the design leans on them

- **F1 (identifier-aware tokenizing), partly.** The numbers are in the paper (section 7, table 5 and the text after it, https://arxiv.org/html/2605.18561): Go 0.309 to 0.563 (+82%), Java +27.8%, Ruby +22.5%, Python +0.3% (whitespace-only +17.5%), q-log on top of the identifier-aware tokenizer +0.2%. Three things are off:
  - The BEIR control (NFCorpus, SciFact, ArguAna) tests only the paper's IDF change under the fixed generic tokenizer. The identifier-aware tokenizer was never run on prose, so "neutral on prose" in ladder step 1 has no support in this paper.
  - The quoted sentence "the tokenizer change captures nearly all of the improvement" is not in the paper. Its wording is "identifier-aware tokenization largely removes the incremental gain from q-IDF" and "q-log adds little once identifier-aware tokenization is used".
  - The table is a 50K-document subset of one language, in a single v1 preprint about a different method (the headline result is 0.2575 to 0.4874 on the full 182K Go corpus with the generic tokenizer). The baseline is the bm25s default (lowercase, stopword filter, `\b\w\w+\b`, no stemming). Sub-tokens only scores 0.469, below whole plus sub-tokens (0.563); whitespace-only halves Go (0.149) and is the best on Python. The paper's own advice is a tokenizer "matched to the language's identifier morphology".
- **F27 (Letta file agent), partly.** 74.0% on LoCoMo with GPT-4o mini against Mem0's reported 68.5% is as written (https://www.letta.com/blog/benchmarking-ai-agent-memory). But the tools are not plain file tools: "Files in Letta are automatically parsed and embedded to enable semantic (vector) search", `search_files` is that vector search, and tool rules force the agent to start with `search_files`. It is evidence for an agent that searches repeatedly, not for grep-only recall.
- **F30 (abstention preprint), partly.** 162 of 164, 85 of 166, 0.825, 0.697 and 0.806 are in the paper (https://arxiv.org/html/2609.18672). What the summary leaves out:
  - The seven-candidate sets "always contain gold" and the other six are sampled at random. It is an upper bound for a scope filter that never drops the right row, not a measured filter. Ladder step 3 cites it as if it were.
  - 0.697 is the BM25-feature gate on paraphrases against out-of-catalog only. The same gate reaches 0.959 on lexically matched requests and 0.831 overall, so a lexical gate is good exactly where the match is lexical.
  - Query length alone reaches 0.741, above the combined 0.697, and the author says length separates the sets partly by construction. The data is 600 synthetic Korean and English requests over 70 tool descriptions, one author.
