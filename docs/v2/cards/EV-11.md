# EV-11: ownership and size checks

**Plan:** section 6 (the size budget, before 6.0), section 8 Stage 1 row EV-11 and "What runs in parallel", section 9 ("Rules that keep parallel work safe"), decision 26. **Design:** `docs/v2/working-papers/design/evaluate.md` section 12.3 and its row EV-11; `critique-simplicity.md` issue 1, which set the budget and shrank the row. **Size:** S. **Reviewers:** one. **Depends on:** EV-12 (merged: `eva-eval` and its `register`). The plan's row names EV-10; nothing here reads what EV-10 writes.

## Why

Two rules of section 9 are only words today: a diff stays inside the paths on its card, and the Go built into the binary, net of v1 lines scheduled for deletion, is no larger than v1's 53,694 lines. With several builders at once, a rule nobody checks is broken by accident. This package makes CI check both. It changes nothing eva-md does, so it needs no switch.

## What to build

1. **Two blocks a card can carry**, read by code. A fenced block with the info string `paths` in "Owns and may touch": one pattern a line, either an exact file or a folder ending in `/**` (everything under it). A fenced block with the info string `deletes`: the v1 files or `/**` folders the package schedules for deletion. This card carries its own `paths` block. State the format in the package's doc comment.
2. **`eva-eval paths [--repo dir] FROM TO`**, from `cmd/eva-eval/guard.go` with `register`. It walks the first-parent commits in `FROM..TO`. Each is judged on its diff against its first parent, renames as two paths, by the cards its `Card:` trailers name (one or more), each read from that commit's own tree, `docs/v2/cards/<ID>.md`. It fails, with one line naming the commit, the card and the path, on: a path outside the union of the cards' patterns; a card that does not exist; a card with no `paths` block. A commit with no `Card:` trailer is the lead's: listed as such, not judged. Exit 0 or 1, and 2 for a usage error or a repository it cannot read.
3. **`eva-eval size [--repo dir]`**. Built lines: the newlines in the non-test Go files of the main module that `go list -deps ./cmd/eva-md` gives with `GOOS=darwin`, `CGO_ENABLED=0`, no build tags, for `arm64` and `amd64` together, as `listRelease` in `cmd/eva-md/licenses_test.go` lists a release. Scheduled lines: the built lines of files that a `deletes` block of a card whose state in `docs/v2/cards/README.md` begins with `merged` matches, counted once, and only files that existed at v1's commit `51b241c`, the last before the v2 plan (tests pass their own, as they pass the ceiling). No card index means nothing is scheduled. An exact entry naming a file v1 did not have is a fault. It prints the built, scheduled and net lines, the ceiling and the headroom, and exits 1 when net exceeds 53,694, a constant in the package. Once the index lists `CUT-4` as merged, nothing subtracts and a scheduled file still present is a fault: the plain ceiling.
4. **A CI job**, `guards`, in `.github/workflows/ci.yml`, on `ubuntu-latest`, with the whole history. It finds the base as the `latency` job does and runs `go run ./cmd/eva-eval paths "$BASE" "$SHA"` and `go run ./cmd/eva-eval size`. `TestNoReleaseBuildsIt` allows `./cmd/eva-eval` in `ci.yml` alone; every other workflow and script still builds `./cmd/eva-md` alone and nothing names live-accuracy.

## Accepted when

- `scripts/linux-check.sh` passes, and `go list -deps ./cmd/eva-md | grep -c internal/eval` prints 0.
- On a small git repository the test makes in a temporary folder (`testgitenv.Clear()` in `TestMain`): a commit inside its card's paths passes; a seeded commit that adds, deletes or renames a file outside them fails, named; so do a missing card, a card with no `paths` block, and a commit that widens its own card's block; a commit with no trailer is listed and passes; a merge's second-parent commits are not judged alone. `a/**` matches `a/b/c` and not `ab/c`.
- On a fixture module with a temporary `HOME`, `GOTOOLCHAIN=local` and `GOPROXY=off`, the count equals a hand count: a darwin-only file counts; a `_test.go` file, a linux-only file, a file under another build tag and a package nothing imports do not.
- The ceiling is passed to the counting function, so one test passes at the ceiling and fails one line over it. A merged card's `deletes` subtracts and an unmerged one's does not; with `CUT-4` merged nothing subtracts.
- The report gives the `size` output with `--repo` on a checkout of `51b241c`, which must be 53,694 (if not, stop and report the difference; never change the constant), and on `main` today. If `main` is over, say by how much: scheduling deletions in merged cards is the lead's, before this package merges.

## The lead's rulings of 2026-11-13, given with the order

- **Where the `Card:` line stands.** Since 2026-11-11 a commit that lands a package carries `Card: <ID>` on a line of its own straight after the subject, not in the message's last paragraph, so git's own reading of trailers does not find it. The check reads such a line wherever it stands in the message.
- **The cards written since.** Every card that is not merged and has no `paths` block gets one from its "Owns and may touch" as written; the builder lists the cards whose words name no exact paths, and the lead writes those.
- **The size check does not fail CI yet.** No card has a `deletes` block, and those are the lead's to write. Until they are written, `size` runs in a step of its own that shows its figure and does not fail the `guards` job, so that a count the lead has not settled blocks no release; `paths` fails the job from the start. The builder reports the built, scheduled and net lines of `main` as it stands, and by how much it is over if it is.

## The size check's first reading, 2026-11-13

`eva-eval size`, run by the builder on `main`: 63,236 built lines, 9,542 more than v1's 53,694. Three readers, one working from the plan's words, one from the code and one judging both, found one deletion a merged card can book today: `internal/okfadapter/**`, 1,038 lines, on ST-03a, the codec that replaces the page library's adapter (plan section 6.0). With it the net is 62,198, which is 8,504 over. The lead writes that block when this package merges.

- **What the growth is.** 8,888 lines are in files v1 did not have, which no `deletes` block can subtract, and 654 are inside v1's files. The counters release and `audit shapes` make 6,465 of it: `audit shapes` 1,959 (HF-01), `audit capture` 1,818 (CT-3, CT-3b), `doctor --report` 1,317 (CT-4), the update counters 735 (CT-2) and the hook counters 636 (CT-1). The rest is v2's first parts: the event model and its reader 1,165 (LG-10), the seams 736, the host adapter 616, and redaction's driver and switch 560.
- **Why no other block is written.** A block says that a merged package replaces the code it names, and it freezes that code (plan section 9). `internal/hook/trigger.go` is DV-26's to delete, `internal/update` is the organizing track's, and DV-02a, which is not merged, still changes `cmd/live-accuracy`. To book the whole of CUT-4's list on merged cards would bring the figure under the ceiling while nothing had been replaced.
- **What the plan's rule cannot do.** The plan asks that the net figure hold "at any merge", and its own Stage 1 packages delete nothing before the cut-over. So `main` reads over the ceiling until Stage 2's deleting packages merge, whatever blocks are written.
- **The end state, which is an estimate and not the tool's count.** The deletions the plan names by file come to about 16,300 lines, and to about 22,000 with those it names loosely. Against them stand today's 9,542 lines of growth, about 7,000 lines of merged v2 code that nothing calls yet (the codec, the migrator, the format checker, the worker and the store's interface), and all of Stage 2's new code. Without a change, v2.0 is unlikely to meet the budget.

So `size` stays a step that reports and fails nothing. Two questions went to the owner, whose decision 26 it is, and the owner left the judgment to the lead. The ruling is in the plan (section 7, "Where the decisions stand"): the ceiling stays 53,694 and binds at CUT-4, with the figure reported at every merge until then; and the counters release's instruments stay in the release while v1 is the product and leave the binary at CUT-4 unless a v2 package has taken their work over inside the budget. Owed: the ledger of what leaves and when, file by file and package by package, that the critique which set the budget asked for (`critique-simplicity.md`, open question 4), with those instruments in it; the lead brings it to each stage's readout.

## As merged

Merged from `pkg/ev-11-r1` on 2026-11-13, after a review, a fix round and a verification that accepted it. A first builder had been cut off part way; the second carried on from its three commits. What the review changed:

- **A slip of the pen is a fault, not the lead's commit.** A line that sets out to name a card in another form, such as `Card: AA-1, AA-2`, a lower-case `card:` or an indented line of a squash message, used to make the commit the lead's, listed and never judged. It now fails the commit. So no line of a commit message starts with `Card:` or `Cards:` unless it is a card's line.
- **A commit cannot give itself room.** A card its first parent did not have, or whose block could not be read there, counts as one with no paths: the lead commits a card, or a wider block, in a commit of its own before a commit names it.
- The size count ignores a developer's go env file, and a block's entry with a space or a backtick is refused.

On `main`'s own history the check finds no malformed line. Its faults there are old ones: cards that had no block when their packages landed, and three paths outside a block in commits of CT-3b and HF-01. The job judges only the commits a push brings, so they fail nothing.

For the lead, from this merge on: `go run ./cmd/eva-eval paths origin/main HEAD` before a push says what CI's job will. A follow-up to a merged card that has no block lands as a lead's commit with no card's line, or after the lead has given the card a block. HF-00 keeps its block, since its Part 2 may come.

Owed: a `paths` block from the lead for each card whose words name no exact paths (DV-13, EV-10a, EV-10b, HO-12a, HO-12b, and EV-17d once its builder has named its files; all written by 2026-11-13 but DV-13's, which waits for DV-12b's files); a second look at two blocks made from a reading of the card's words (DV-12b's "the two tests named in item 5", HO-12c's "their tests"); and the ledger named above.
