# EV-12: the results store and gates

**Plan:** section 6.6, section 8 Stage 1 row EV-12 ("Every result is a row with commit, host version and model; better or worse than the accepted baseline is one command"). **Design:** `docs/v2/working-papers/design/evaluate.md` sections 4, 5 and 7, and its row EV-12 in section 21. **Size:** M. **Reviewers:** one.

## Why

Principle C of the plan: nothing ships unless a measurement moves. That needs one place where every measurement lands as a row that says what was measured, on which commit, host version and model, and one command that says whether a number is better or worse than the baseline it must beat. Every instrument (fidelity, retrieval, latency, continuation) writes to it.

## What to build

A harness that no release contains: `cmd/eva-eval` (a separate program) and `internal/eval/results`. `go list -deps ./cmd/eva-md` must not list either.

1. **Rows.** One append-only file of results under a folder the caller names (a path in the repository for committed baselines, any folder for runs). A row carries: the metric's name, its value and unit, the commit, whether the tree was dirty, the instrument and scenario, the host and its version and the model where one was used, the seed, and the time. No row holds captured text, a codename from a scenario, or a path under a home folder.
2. **A catalogue of metrics** (one file): each metric's name, unit, direction (lower or higher is better) and the paths of the repository whose change makes a stored baseline stale.
3. **Gates as data** (one file): each gate names a metric, a comparison with the accepted baseline (not worse by more than a stated margin, or better by at least one) and the statistic used.
4. **Commands:** `eva-eval gate` (exit 0 when every gate holds, 1 when one fails, with one line for each gate), `eva-eval diff` (two sets of rows, side by side), `eva-eval baseline accept` (writes the accepted baseline from a set of rows, refusing a dirty tree). A baseline is stale when a path its metric lists has changed since the baseline's commit; a stale baseline fails its gate with a message that says so.
5. **Statistics** follow evaluate.md section 7: exact figures from the rows, a fixed seed wherever resampling is used, and no model anywhere.

## Owns and may touch

`cmd/eva-eval/**` and `internal/eval/**` (both new). Their test data.

## Must not touch

Everything else. `cmd/live-accuracy` and `internal/update/accuracy` stay as they are; EV-14 replaces them later.

## Accepted when

- `scripts/linux-check.sh` passes, and `go list -deps ./cmd/eva-md | grep -c internal/eval` prints 0.
- Fixture rows give exact statistics under a fixed seed, by test.
- A doctored row flips a gate, by test, in both directions.
- A codename planted in a scenario's input is found in no row and no report, by test.
- A baseline goes stale when a covered path changes, by a test that makes a small git repository in a temporary folder (with `testgitenv.Clear()` in `TestMain`).
- No new module; only eva's name in any output.
