# DV-13: the cost ledger, a token budget, and a low effort by default

**Plan:** section 8, Stage 1, row DV-13; decision 5, at its recommendation; section 5.4, the row on what the background run costs; section 6.3, design 8; section 9 (a named exception to the freeze of v1's update); section 13.3, point 1. **Design:** `derive.md` sections 3.5, 8.3 and 9, and its row DV-13 in section 18; `audit/update-model.md` section 1.5 and finding F5. **Size:** S. **Reviewers:** one. **Depends on:** DV-12b and CT-2 merged (they change `runlog.go`, `cmd/eva-md/work.go` and the `status --updates` report); LG-12 first if both are open (both edit `config.go`).

## Why

v1 organizes on the chat's model at the highest effort and counts calls, not tokens, though both hosts report them. On the real install a pass took a median of 124 s and about 41,000 tokens; nothing totals the cost. This package makes what organizing spends one number, gives the worker a token budget to obey, and puts decision 5's interim default, the chat's model at a low effort, behind a switch, ready to ship once the counted week is read.

## What to build

1. **Two switches** in `internal/config/cost.go` (new): `LowEffortDefault = NewBoolSwitch("low_effort_default", false)` and `TokenBudget = NewBoolSwitch("token_budget", false)`. Both off is v1, byte for byte.
2. **The low default.** With `LowEffortDefault` on, `Config.EffortFor` returns a new `EffortLow` (`"low"`) where it returns `"highest"` today. An `[effort]` entry still wins, and the model stays the chat's. A pass (`run.effort`) and `Live` both follow.
3. **Cached input apart.** `Result` and `attempt` (`runner.go`) gain a cached count: Claude's `cacheReadInputTokens` (`modelUsage`) or `cache_read_input_tokens` (`usage`), Codex's `cached_input_tokens`. `Record` gains `TokensCachedIn` (`tokens_cached_in`, omitempty), set in `run.call`. `tokens_in` keeps its meaning; a cache write counts as uncached input; a record without the field has no cached input.
4. **The ledger**, `internal/cost` (new), standard library only: `Usage{In, CachedIn, Out, Calls, MS int64}` (`In` uncached), `Add`, `Weighted()` = `(10*In + CachedIn + 50*Out + 9) / 10`, `Estimate(bytes)` = `Usage{In: (bytes+3)/4}`, and `Week`: `Usage`, `Passes`, `Organized` (sessions with an `ok` or `no_change` pass), `NoChange`, `BelowEffort` (`effort_used` below `effort`), `PerChat()`.
5. **From the run log**, `internal/update/cost.go` (new): `Spent(records, host, now)`, today's `cost.Usage`; `OverBudget(c, records, host, now)`, true when calls reached `daily_cap` or, with `TokenBudget` on, weighted tokens reached the budget; `Week(state, host, now)`, the last 7 days. `update.Host`, which the chat-start notice runs, is unchanged.
6. **The budget.** Key `daily_token_budget` (`Config.DailyTokenBudget int64`, omitempty): weighted tokens a host a day; 0 or absent means `DefaultDailyTokenBudget`, 1,000,000, provisional until DV-03; negative fails `Validate`. With `TokenBudget` on, `run.hostStop` stops a host whose tokens today reached it, and `run.gate` one whose tokens plus the pass's `Estimate` (bytes of `Rules`, the input and the schema) would pass it: `StopBudget`, logged as `about N of M thousand weighted tokens today`. That defers: no record, the watermark stays. `daily_cap` still applies, a person's run included.
7. **The worker obeys.** The update job's `Waiting` (`cmd/eva-md/work.go`) gives `WaitBudget` when `update.OverBudget` is true, in place of its own `daily_cap` test.
8. **One number, and the week.** With `TokenBudget` on, `updateRow`'s detail (`internal/health/background.go`) adds `about N thousand weighted tokens today, P% of the day's budget`. `internal/health/cost.go` (new) writes a section of `eva-md status --updates`, called once from CT-2's file: per host over 7 days, each token count and the weighted sum, calls, organized chats, tokens per organized chat, and the shares unchanged and below the effort asked. Numbers only.
9. Give in the report the lines `docs/design.md` and README need for the key, the switches and the weighting.

## The lead's rulings of 2026-11-14

The paths block above is the lead's reading of "Owns and may touch"; where the two differ, the block and these rulings hold.

1. **The switches are registered in `internal/update/cost.go`, not in `internal/config`.** `TestNoSwitchIsRegisteredHere` holds the config package to one switch, redaction's, and no existing test changes. `update.LowEffortDefault` and `update.TokenBudget` are registered where they switch; health and the CLI already import `internal/update`. There is no `internal/config/cost.go`.
2. **`Config.EffortFor` keeps its meaning.** `internal/config` gains the constant `EffortLow` (`"low"`) and a way to tell an entry from the default, such as `EffortEntry(host, model) (string, bool)`, which `EffortFor` then calls. `update`'s two callers (`live.go` and `pass.go`) go through one function in `internal/update/cost.go`: the entry where there is one, else `low` with the switch on, else `highest`. `internal/config/cost_test.go` (new) holds the field, `Validate` and the new method.
3. **"CT-2's file"** is `internal/health/updates.go`, where `status --updates` writes its lines: the one call goes there.
4. **Documents.** The design is split (EV-10a): give in the report the lines for `docs/spec/update-job.md`'s "Since the split" (the key, the switches and the weighting) and for README.md's config keys. The lead writes them at the merge; neither file is in the block.
5. **The latency gate** is run once when the machine is quiet (the first load figure under the CPU count); a verdict of `not judged` is reported as such, and CI's `latency` job on the merge is the run of record.

## As merged

Merged on 2026-11-14 from `pkg/dv-13-r1`, after one review (contract: six minor; the three test gaps mended, with each mutant seen to fail) and a verification that accepted it. Both switches are off by default; off, the goldens of `status` and `doctor` pass and only `daily_cap` stops the job, by test. In the merge the lead renamed one helper of `internal/health/cost.go` (`passShare`), whose name HO-12b, merged an hour before, had taken in the same package, and reworded the comment on `StopBudget` in `internal/update/job.go`, which the paths block did not hold.

**The lead's rulings at the merge.**

- **The budget stops a person's run too**, as built and as `daily_cap` does: the card's "a person's run included" covers both, and a test now holds it on both paths (the day's spend and a pass's estimate).
- **The week's cost line and the row's token detail show only with `token_budget` on**, as built: with both switches off `status --updates` is v1's, byte for byte, which the card asks for. That a person must turn the budget on to read the week is a known gap; the card that fixes the budget (after DV-03's figures) decides whether the line shows by default, and whether it enters `status --updates --json`, which needs a new format of the field report, since that report embeds these figures and pins its keys.
- **The worker's wait** is turned in `cmd/eva-md/work.go` (`budgetWaits`), not in `internal/health/work.go`, which was outside the block: only a wait for the size or quiet rule becomes a wait for the budget, and only with the switch on.
- **`daily_token_budget` is tagged `omitzero`**, since the TOML library omits a zero number only so.

**Known and left** (docs/known-limitations.md has the first): a budget smaller than one pass's estimate defers that batch every day, and only the job's log says why; `cmd/live-accuracy/trace.go` does not record the cached input; `update --dry-run` shows the low default through `run.effort`, with comments in `dryrun.go` that say less. `TestWatermarkFailureStaysWithinTheBudget` fails for root by design.

**The latency gate.** `not judged` on the cloud machine (load 3.6 to 4.9 on 4 CPUs), every scenario ok and the medians flat; CI's `latency` job for the merge is the run of record. A hook reaches only the new config field, one comparison in `Validate` and the switches' registration.
