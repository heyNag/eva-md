# DL-04: the labelled retrieval set and its scorer

**Plan:** section 8 Stage 1 row DL-04; section 6.6 (the retrieval instrument); section 6.4 (design 4 and "Later, on a trigger"); section 5.4 (wrong context, at most 1% of additions on a held-out set); section 12 (lexical matching and embeddings, whose triggers read this set); section 14.4; decision 13. **Design:** under `docs/v2/working-papers/`, `design/deliver.md` sections 3.6 and 3.8 and its row DL-04; `design/evaluate.md` sections 4.1 and 6.2; `audit/recall.md` F5. **Size:** M. **Reviewers:** one. **Depends on:** EV-12 (merged).

## Why

v1's recall was tuned and judged on the same 73 prompts, with no held-out set. DL-06 must show that v2's retrieval core is not worse than v1, and section 12's triggers wait on held-out figures. This package builds the set, the scorer, and v1's recorded row. Its `System` interface is the retrieval core's contract, which DL-06 implements and IF-01 fakes. Nothing in eva-md changes, so there is no switch.

## What to build

1. **The set**, under `eval/retrieval/set/`: made-up projects, items and events, generated by code with a fixed seed or written by hand. If generated, a test regenerates it and compares bytes.
   - At least 500 items in at least 3 projects. Item fields use the names of `docs/spec/store-format.md` section 10: `id`, `type` (the five kinds), `project`, `scope`, `title`, `statement` (at most 150 characters, so v1's three fit its 1,000-character block), `cues`, `words` (rules and constraints only), `paths`. `projects.json` lists each project's key in v1's form and the groups of projects that share a system page.
   - At least 800 events, each a typed prompt: `id`, `project`, `first` (the chat's first prompt), `text`, `split` (`lexical`, `paraphrase` or `name`), `class` (`positive`, `no_match`, `near_miss` or `sibling_only`), `relevant` (item ids, empty for the last three classes) and `decoys` (the items it was built to tempt).
   - A sibling project's item is never relevant (decision 13), though v1 recalls it.
   - Name events: the name is a cue of exactly one item, and of that item's `words` when it is a rule or constraint. In a near miss the name appears as an ordinary word and nothing is relevant.
   - Halves: an event's half (`tuning` or `heldout`) is a function of a hash of its id. `halves.sha256` holds a hash of each half's events.
2. **Package `internal/eval/retrieval`:** types `Item`, `Project`, `Event` and the set loader; `System`, with `Add(ctx, Event) ([]string, error)` returning added item ids, best first (none is silence); `Register(name, build func([]Item, []Project) (System, error))`, called in `init()`, so DL-06 adds its core in a new file; and the scorer.
3. **Systems:** `v1-recall` returns the first `knowledgepage.MaxRecall` rows of `knowledgepage.Recall`, a rule mapped to a constraint, siblings from `systempage.Siblings` over the share groups, and no skip. `silent` and `oracle` serve as test arms.
4. **Measures**, for each half, over each split and `all`: `precision`; `recall`; `false_additions` (additions not relevant, as a share of all additions); `silence_pos` (positive events with no addition); `silence_neg` (other events with none). For each negative class, `false_events` (events with any addition). A ratio with no denominator is left out. For a zero count over n, the table prints the 95% upper bound, 1 − 0.05^(1/n).
5. **Rows** through `results.Store`: metric `retrieval.<half>.<split or class>.<measure>`, unit `ratio`, instrument `retrieval`, scenario `<system>.set<version>`. `Forbid` holds every made-up name and project name in the set.
6. **`eva-eval retrieval [--repo dir] [--set dir] --system name --out dir`**, in `cmd/eva-eval/retrieval.go`, which adds the command with `register` from its `init`; `main.go` is not edited. It writes rows and prints a table of figures and ids, never an event's text.
7. **Gate files:** `eval/retrieval/metrics.json` lists every metric, with paths `eval/retrieval/set`, `internal/eval/retrieval` and `internal/knowledgepage`, never the baseline file itself. `gates.json` holds not-worse, margin 0, on the held-out `all` and `name` precision, recall and false additions. `baseline.json` holds v1's row, accepted with `eva-eval baseline accept` from a clean commit. The lead accepts it again on `main` after the merge, which makes a new commit.

## Accepted when

- `scripts/linux-check.sh` passes, and `go list -deps ./cmd/eva-md | grep -c internal/eval` prints 0.
- A test holds the set's shape: the counts above; in each half at least 160 negatives, every class, 30 name events that resolve and 30 name near misses. Every relevant id exists, and none is a sibling project's.
- A test checks the labels: each name is a cue of exactly one item, and a paraphrase shares no word of 3 or more letters with its item's title or statement, beyond a short list the set declares. A near miss shares at least two such words with each decoy.
- Changing one held-out event fails the halves test until `halves.sha256` changes.
- On a hand-built set of five events, a fake system gives exact figures for every measure, and one added sibling item raises `false_additions` by exactly one addition. Zero in 160 prints a bound under 1.9%.
- A test shows `v1-recall` adds a sibling project's item only when the two projects share a system page.
- Two runs give identical rows apart from time. The values in `baseline.json` equal a fresh `v1-recall` run on the committed set. A planted name in a scenario id makes the Store refuse the row, and no planted name is part of any id the scorer writes.
- No new module, and only eva's name in any output.
