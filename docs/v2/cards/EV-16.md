# EV-16: latency that can fail a build, and a baseline before any hook changes

**Plan:** section 6.6 (the latency instrument), section 8 Stage 0 row EV-16, section 9 ("One timed check is also a merge gate"), section 13.3 point 5. **Design:** `docs/v2/working-papers/design/evaluate.md` section 6 (the paragraph on latency) and its row EV-16. **Size:** M. **Reviewers:** one.

## Why

Hooks must stay fast: capture under 50 ms and a chat-start brief under 300 ms at the 95th percentile, and v2 wants the brief under 150 ms. Today the benchmark reports and nothing fails. On the one real install the brief took 0.92 s to build by command, three times v1's own target, and the benchmark has no scenario that would show it. Every later package touches a hook, so the gate and a baseline must exist first.

## What to build

1. **Scenarios from a list.** The scenarios `scripts/benchmark.py` runs come from a list each scenario adds itself to, so a later package adds one without editing `main`. The script still runs with `python3 -I`, prints the same report for the same binary, and keeps every target it checks today. If scenarios move into files of their own they load from the script's own folder by an explicit path, since `-I` ignores the current folder.
2. **Three scenarios added.**
   - *The shape of the real install:* an inbox of 600 session files in one area, one of 2 MB and the other 599 sharing 2.3 MB, most of them holding an end event and little else, with a wiki of 54 pages (39 knowledge pages, 4 thread pages, a rules page, 4 system pages and 6 others). It times a chat start, a prompt and a capture there. Content is generated and made up.
   - *A whole turn of 50 tool calls:* the processes started and the milliseconds summed, for each host's hook declaration.
   - *Process start counted:* every hook figure includes the start of the process, on each host's launch path, and the report says so.
3. **A gate mode.** `scripts/benchmark.py --compare OLD NEW` runs the two binaries in alternating runs on the same machine and exits 1 when, for any gated metric, the lower bound of the bootstrap interval (fixed seed) of the ratio of the new 95th percentile to the old is above 1.15, or an absolute ceiling is passed (on CI the ceiling is twice the target). In the same run it compares NEW with NEW as a control. If the control itself fails, the machine was too noisy to judge: the gate then exits 0 and says "not judged", and never fails a build on noise.
4. **The macOS job runs it.** A step in the macOS job of `.github/workflows/ci.yml` builds the binary of the commit before the change (the push's parent, or the pull request's base) and of the change, runs the gate, prints the report, and saves the report as an artifact of the run. The step starts as advisory (it reports and does not fail the job); the lead makes it blocking after an unchanged binary has passed twenty times in twenty. No other job and no release workflow changes.
5. **A baseline file.** The format and the place of the stored baseline, `docs/v2/baselines/latency-macos.json`, with a short note beside it on how the lead refreshes it from the macOS job's artifact. The builder commits the format and a first file measured on Linux, marked as such; the lead replaces it from CI.

## Owns and may touch

`scripts/benchmark.py`, a new `scripts/bench/` folder if scenarios get files, the macOS job of `.github/workflows/ci.yml`, `docs/v2/baselines/**`, and `scripts/linux-check.sh` only if the benchmark's call must change (prefer that it does not).

## Must not touch

Any Go file. `.github/workflows/release.yml` and `cut-release.yml`. The Linux job of `ci.yml`. If a test in `internal/release` pins the text of `ci.yml`, change only what that test needs and say so in the report.

## Accepted when

- `scripts/linux-check.sh` passes, and the benchmark's report for the same binary holds the same lines as before for the scenarios that existed.
- The gate fails a binary with a seeded 20 ms delay in capture (build it in a scratch worktree for the test, do not commit the delay), and passes an unchanged binary against itself in 20 of 20 runs on this machine; report the 20 results.
- A noisy control yields "not judged" and exit 0, shown by a test of the decision function on made-up samples.
- The decision function (samples in, verdict out) has unit tests that run with `python3 -I` and no timing: they feed it numbers.
- The three scenarios run and print their figures; the real-install scenario's figures are in the report so the lead can read v1's chat-start time at that shape.
- The CI step is syntactically valid (the workflow file parses; `actionlint` if it is installed), uses only actions the file already pins by commit, and needs no secret.
