### Changes to decisions

Where this design refines a decision in [decisions.md](../decisions.md), and why.

| Decision | Change | Why |
| --- | --- | --- |
| 1. The wiki lives in a private repo | Private, or internal after you agree, when the host's admins forbid private repos or the repo you give is internal: setup tries private first, asks before it creates or uses an internal repo (no is the default), takes `EVA_MD_ALLOW_INTERNAL_REPO` as the answer in advance (`true` agrees to any internal repo, on any host), and refuses one without a terminal or a yes. A public repo is always refused. A bare repo on this Mac also holds a wiki. | A self-hosted GitLab can restrict private visibility to its admins, so a private repo there is impossible for anyone else; the user decided that an internal repo, readable by everyone signed in to that host, is acceptable once they agree to it. |
| 1. You create the empty repo; never GitHub or GitLab APIs | Only `eva-md setup` may run gh or glab, and only when it is installed and signed in: `auth status`, `config get` (the git protocol and glab's host), `repo view` and `repo create`, to create the wiki's private repo, or an internal one once the user agrees where the host's admins allow no private repo, to check that a repo is private, and to read back a repo's address, also to clone a missing wiki folder again. Reading a repo's schema before using it is plain git. The wiki, init's git steps, the hooks, the update job and the daily commit and push stay plain git. | Creating the repo was the one manual step left, and a public wiki repo is the costliest mistake setup can catch. The CLIs keep the user's own login, and nothing after setup depends on them. |
| 1. The platform uses only the plain git command line | `eva-md upgrade` and the install and uninstall scripts download eva-md's own releases from github.com over HTTPS (`releases/latest` and `releases/download/<tag>/<name>`), with no API call and no sign-in. Nothing else does, and hooks never do. | A one-command install and upgrade needs the release files, and public files over HTTPS need no token and no API. |
| 4. Hooks save every exchange word for word | An exchange is your prompt plus the final assistant message, plus one-line tool records (successes and failures), plan updates where the host has them, and Claude's compaction summary, except once the chat has been off the record, until a startup or clear chat start. Assistant narration between tool calls and all tool output are not saved. Prompts you didn't type are saved as events. | These are the documented payload fields (Claude's `last_assistant_message` is the final reply only). Transcript formats are not a stable interface, and tool output is where secrets and noise live. |
| 5. After each chat, a detached job runs the update | "After each chat" means any of: SessionEnd, PreCompact, a 60 KB backlog at Stop, the next prompt after a 30-minute gap, or catch-up at the next chat start, with the day's sweep of up to 5 backlogs idle an hour or more at a person's first chat start of the day. At most 40 model calls per host per day, at the configured effort. Codex's 30-minute SessionEnd counts only for chats closed in every client. | Desktop chats rarely end and long chats rarely compact. There is still no model call per turn and no sleeping process. |
| 5. ...with tools off | Claude: tools off (`--tools ""`). Codex: each tool feature on eva-md's list (Codex 0.166.0's) that `codex features list` names is disabled, and any run that still used a tool is rejected and retried later. | Codex ignores the opt-out for unified exec, and several tool features stay on unless disabled one by one. Rejecting tool use enforces the intent. |
| 5. Promotes lasting facts into wiki pages | Lasting facts are kept as dated, sourced Timeline lines on the branch's thread page, and the update promotes those that pass the six-month bar into knowledge pages, from the batch it reads: one statement a page, superseded or dropped with a History line, never deleted. Chats a pass has already covered are not read again for it. | Refs can name only the batch's entries, so only what the batch states can be checked, and a backfill over earlier chats is ruled out. |
| 6 and 16. Strong matches on a prompt are added quietly; knowledge pages come after day one | Knowledge pages, the recall skill and prompt recall were planned to start after two weeks of daily v1 use. They were built at the user's request on 2026-11-02, rather than after two weeks of daily v1 use: a prompt that strongly matches gets the fact itself (at most 3 facts in 1,000 characters, label and fence included, 900 until the label came to say what the tags rest on; weak matches add nothing), only the background update writes knowledge pages, and a new chat's brief lists the project's constraint pages only (within 600 characters). okf's team-sharing features (registry, vendor bundles, hub sync, scope layers, scorecards) stay out. | The user chose to have them now. Each part is checked offline against fixtures, recall reads one local file, and a second small one only to tell which projects share a system page, within the prompt hook's latency target, and `recall = false` turns it off; the floor and the promotion bar are still to be judged in real use. |
| 5 and 6. After each chat, a job runs the update; a new chat resumes the previous one | A Claude chat a program runs (`claude -p`, the Agent SDK, told by `CLAUDE_CODE_ENTRYPOINT`) is captured, but asks for no update of its own, is passed over by the update as `skipped (headless)` with no model call, and is never the brief's previous chat or lineage pick. | A program's prompts are stored as events, not as your words, so a thread page or a resume built from them would rest on no prompt you typed. |
| 6 and 16. The agent searches further on its own; search comes after day one | Deterministic, agent-initiated search over the inbox, the thread pages, the system pages and the knowledge pages (`eva-md search`) is part of v1. On prompts, v1 adds pointers to the system pages a prompt names, matched by name with no model, the knowledge a prompt strongly matches, scored by words with no model, and a short reminder of the two commands. | When the agent ran follow-up searches it found everything 10 times out of 10, and the inbox already holds every exchange word for word. A scan needs no model, index or MCP server, and it never runs in a hook. |
| 6 and 16. Search: the scan | Once history spans years, the inbox gets a rebuildable search index, a cache built from it that search reads beside the scan, with the scan as the fallback whenever the index finds nothing. Matching in indexed files is by whole tokens and word starts, and equally good hits rank by BM25 before newest. | A scan costs 1.7 to 2.9 s per GB for a rare word, and a common one is cut at the 5-second limit, more each year. Every line the index proposes is read again from the inbox, so it never changes the text of a hit; in indexed files a match inside a word, or in text without spaces, goes unseen next to other hits. |
| 7. One commit a day, one signing approval | The day's commit starts at the first hook event of the day, not only at a chat start. One signing attempt per day. A refusal is not retried until tomorrow or a manual `eva-md commit`. The SSH push may need a second approval, depending on your signing and SSH agent setup (not yet counted; see Open host questions). | A missed prompt must never turn into a stream of prompts. Signing is never changed. |
| 9. One binary also serves as the MCP server | It does: `eva-md mcp` is a read-only MCP server over `eva-md search`, `eva-md show` and a project status, which the plugins start once a chat. It writes nothing, and the brief's footer and the prompt reminder still name the command line. | Nothing in the resume path needs MCP, so the server only adds tools, and the command line works where a host didn't connect it. |
| 11. Each project has a Now page with a dated timeline | The Now and Timeline content lives in per-branch thread pages. The project's now.md is an overview of its threads, built by code. | Decision 16 chose one thread per branch plus a short overview. |
| 11 and 15. okf owns the page format; the generated index; append-only logs | okf owns page parsing, serializing, single-file writes and validation. eva-md writes every file of the scaffold but its pages, the root index.md included; `okf.InitBundle` is still called and writes nothing. eva-md also writes **log.md** (local dates, oldest first, union merge; a line for each page saved, once a day) and the **index.md files** (sorted, in okf's exact line format) itself. `AppendLogEntry`, `UpdateParentIndex` and `RelateConcepts` are never called. Both stay in eva-md until an okf release covers them. | okf's log is newest-first with UTC dates and no append mode. Its index appends unsorted, never prunes, and can't be rebuilt after a rebase. `RelateConcepts` always logs. |
| 12. The next chat catches up on anything a hook missed | Catch-up fills missing turns only for sessions that fired at least one hook, so the transcript path is known. Chats where no hook fired are reported, not swept from host stores. | Sweeping host stores amounts to the ruled-out history backfill, on unstable formats. |
| 12. Codex needs re-approval after each update | Keep the Codex plugin folder byte-identical across binary-only releases and call a binary at a stable path. The doctor and a needs-trust notice still catch a lapse. | On Codex 0.164.0, trust and capture survive a binary-only replacement and an identical reinstall. A description-only manifest change marks all seven hooks as modified until the exact folder is restored. |
| 12. Accuracy and scope suites | Both are written fresh: an accuracy suite of 12 fact scripts, one per known failure mode, whose obligations code derives, which is built, and a scope suite, which is planned. | Fact scripts let code derive every obligation and check the enforceable ones after every output. |
| 13 and 15. Its own names; okf at the core | eva-md shows its own name only. okf is named nowhere you see: not in `eva-md version`, the doctor, a message, an error or the run log, and not in a new wiki's files. A save that fails on okf's temporary file or its lock file says the step that failed in eva-md's words. The root index is eva-md's own, written before `okf.InitBundle` runs, and has no `okf_version` line, which okf's spec makes optional; `.gitignore` covers okf's temporary files with `.tmp-*`; `.eva-md/schema.toml` records no okf version, so the doctor compares none with the binary's. okf still names its own temporary files `.tmp-okf-*` and its lock file `.okf-write.lock`, which eva-md can't change without patching it, each release's `LICENSES.txt` carries okf's license, which asks to go with every copy, and these docs credit it. | eva.md is the front-facing name, and the name of a library under it reads as another product's message or as a fault. Every okf upgrade is checked before it ships (see "Pin and upgrade policy"), while a wiki's recorded okf version was never updated, so after an upgrade the doctor would have failed on every Mac. |
| 15. Protections the adapter adds | The list is no longer "no overwrite on create, one writer, supersede, real host as author". It becomes: no-clobber create, one wiki lock, compare-and-swap, supersede, actor validated before writing, skipping unchanged saves, folder fsync, a body pre-check, guards around LoadBundle, and eva-md-owned log and index files. | okf already records the author through `SaveOptions.Actor` (mutate.go:489-511 in v0.8.0). The real gaps are no validation on write, a fixed clock, no folder fsync, and the behaviours listed in the adapter section. |
| 15. okf owns search | eva-md's search does not use okf's `SearchAdvanced`; it reads its own rebuildable index of the inbox and scans what the index lacks and the thread, system and knowledge pages itself, one file at a time. Prompt recall reads eva-md's own recall index. `SearchLayered` is never used. | `SearchAdvanced` reloads and re-tokenizes the whole wiki for every query. `SearchLayered` depends on the working directory, the home folder and environment variables. |
| 16. Tool activity: files changed and commands run | Edits and commands get one line each, and so do reads, Grep and Glob searches, web fetches and MCP calls, by what they acted on (a path, a pattern, a URL, the arguments), never their output; a web search on Claude Code gets a line with the tool's name alone, never its query or results, so the update can tell a turn that read the web; other tools, such as a subagent, get none (see the plugins' tool matchers). Arguments and URL parts whose names say they carry a credential are left out. | What a chat read, such as a page of documentation or a file, is what a later chat in another repo asks about, so recall needs it, not only what changed. |
| 16. Managed machines: the health check reports managed settings that switch hooks off | Managed settings are not read. The doctor judges a policy by hook heartbeats, and on Codex by the hooks feature that `codex features list` reports; Claude's policy row is UNKNOWN. | Settings-file guesses can't see every managed source, and heartbeats show what actually fires. |
| 16. Visibility: one line at the start of a chat | The routine start line appears on Claude only. Codex stays silent when healthy and shows a line only when something is wrong. | Codex displays systemMessage as a warning. |
