# Verification

This page says what has been checked, and how. Everything built is covered by the automated tests below. The live checks cover capture and resume only: no update has run live yet, and the live checks still owed for wiki updates, system pages, standing rules, pointers and a wiki on a self-hosted GitLab are listed under "Not verified yet". Open problems are listed in [known-limitations.md](known-limitations.md).

## Automated tests

Run them from the repo root:

```sh
gofmt -l cmd internal     # prints nothing
go vet ./...
go test ./...
go test -race ./...
```

GitHub Actions runs the same four checks and the build on macOS for every push to main and every pull request ([ci.yml](../.github/workflows/ci.yml)).

Every test runs against a temporary HOME with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM=1` set, so no test reads or changes the real home folder, the hosts' settings or the user's git config. Fixtures that look like secrets are joined from fragments at run time.

What the suite covers:

- **Redaction** (`internal/redact`). Each secret format, key=value lines in dotenv, YAML, INI and properties files, values with symbols, several secrets in one URL query, form body or connection string, and code shapes that must be kept. `redact.Redact` removes the union of what the baseline rules (`internal/redact/baseline`, frozen) and the current rules remove. Generated-corpus tests check that no generated password the baseline rules remove survives `Redact`, in 16 line shapes and thousands of random passwords. Other tests check that redaction is idempotent on random input, that a SHA or UUID is taken as the value of a secret-looking key but kept in ordinary text, and that identifiers such as branch names and project keys are cleaned without merging two of them, and stay the same when cleaned again.
- **Transcript recovery** (`internal/catchup`). The 1 MiB read window, a row longer than the window scanned in bounded chunks, a row of 256 KiB or more that records an attempt before it is decoded, the cursor saved after every row, slow rows that step down to tighter head-and-tail bounds and then to a gap event, a shorter row whose decoding used up the pass marked slow, a redactor panic that becomes a gap, duplicate suppression, host-generated rows that are never stored as the user's prompts, record controls found in missed rows, also beside an attachment, start-of-chat catch-up finding the newest records first, and recovered rows that never take a subagent's id. A fuzz test checks the row scanner against arbitrary input.
- **Hooks** (`internal/hook`). Every event on both hosts, the folder and remote guards, off-the-record and back on, input, work and output deadlines, malformed input, panics, writes that arrive after a deadline, parallel hooks, the rule that a pending recovery pass stores only event names, and the briefed marker saved only with time to spare before the deadline, for a brief and for a refresh. The hash-triggered refresh on both hosts: a Now updated after the first prompt arrives with the second, the third gets nothing and leaves the marker as it was, and no more than 2 refreshes follow a brief; refreshes after a compact brief, with the count running on through compactions and a /clear starting it again; a marker from before the count, with `"refreshed": true`, counting one refresh used; the marker keeping the project's wiki folder found under another name, the only folder a refresh then reads. A first chat gets the footer alone. The update triggers, through an injected spawn on both hosts: SessionEnd and PreCompact spawn an update for the session, and a chat off the record none; the other events none of their own, though the chat's own file, just changed, holds 120 KB unprocessed and another session of the project idles with a backlog, so a tool line never takes the Stop trigger and a prompt never the catch-up; Stop spawns one at exactly 60 KB unprocessed and not a byte before, after the reply is stored, also with a watermark inside a larger file; a prompt spawns one 30 minutes after the file last changed and not a second before, with 600 bytes unprocessed and not 599, the file read before transcript recovery stores a reply a hook missed, not when an update found that backlog too small, and never for a subagent's or scheduled prompt or a built-in command; SessionStart catches up the project's other sessions idle 2 minutes and not a second less, newest first, at most 5 in one update, leaving out a session processed to its end, one whose rest was found too small and another project's, and reading only the 64 session files the brief lists; a session that start-of-chat transcript recovery has just appended a missed reply to is taken though its file has just changed; the chat's own backlog goes first in that update when its file, as it was before the hook, had not changed for 2 minutes and not a second less, on a resume and on a startup with the same id, within the 5, and its next prompt (with a real clock) spawns nothing more, but not right after a compaction, nor when processed to its end or found too small; Codex Stop's `{}` is written before the spawn; `updates = false`, or a config without a wiki, spawns nothing; and a share folder that is not an absolute path spawns nothing and opens no log, though, from the hook's folder, it names an executable stand-in. A real spawn, from the test binary run as a hook process with a stand-in for the installed binary: the job runs in its own session (its session id is its pid), with stdin from /dev/null, its output in the day's update log (0600), `/` as its folder and the update allowlist with `EVA_MD_INNER=1` (no API key, CLAUDECODE or git config variable); the hook's stdout and stderr reach their end while the job still runs, and the job goes on after the hook has exited.
- **Resume briefs** (`internal/resume`). Every brief variant, lineage only for startup and clear, empty wiki scaffolds, text that tries to forge a speaker header, slow live git, a stray file elsewhere in the wiki that must not cost the brief its Now, and `eva-md show` with a full session id. The Now by priority: a Now of 40 decisions in force, 6 next steps and 3 open questions keeps every next step and open question in the startup, stale and compact briefs on both hosts' caps, shows the newest decisions first with one "more" line for the rest, and shows no hidden comment; at every budget from 0 to 4,200 the renderer stays within it, keeps whole lines only and accounts for every line it leaves out, and from 700 up leaves no room unused that a left-out line would fit, also for a young thread with 30 next steps and no decisions yet; a Now in another format is cut as it is. The size caps: with 71 chats, long messages, a long plan, many tool lines and live git at its limit, every variant on each host stays within its cap, and the startup, clear and compact briefs keep the newest exchange (the newest message and the question before it) and the whole footer though label-like lines and a 40-backtick run lengthen the text; the compact brief keeps its tool activity. The opening request from the head of a 5 MB session file, with a speaker header pasted into it kept on its line, hidden by an off_record event before it, and left out when an exchange shows it. Earlier chats on the branch (at most 3, newest first, without this session's chat or a chat that did no work), other branches (at most 3, newest first) and the tool activity line (the last test command found among other tools, files once each, at most 5). The footer's absolute binary path, named once, its whole text at usual paths, its length without a wiki, its 450-character bound with long paths (the grep fallback left out first, then the thread id), and a first chat's footer alone. The pending line: a startup or clear brief says an update for the previous chat is pending, right below that chat, while its file has a backlog a pass could take, 600 bytes past a watermark and not 599, or any rest of a group a pass stopped in, and not once the update caught up, for a rest it found too small, with updates off or no wiki, in a compact brief or for a lineage chat on another branch. A commit of the commit paths with your signing settings untouched; refusals for another origin or push URL, another instance, an `index.lock`, a rebase, merge or cherry-pick, and a detached HEAD; left-out JSONL, inbox and temp files, paths outside the commit paths, symlinks and secret hits; a busy wiki lock; a push on a run with nothing to commit; a missing remote giving `pending`; a busy push-only run; the lint's oversize pages and bad refs. `maintain`: commit and push, the lint, pruning, a busy lock, `commits = false`, and a push-only run turning pending into ok. The daily trigger spawns maintain once a day, never without an instance or in the headless child, and not after a capture that missed its deadline (`TestLateCaptureStartsNoMaintain`); the push retry's spacing, never retrying a diverged, refused, declined or pushed run, passing over busy and no-op runs. A GitLab set with a fake ssh and an unreachable host: all three remote forms give stable project keys and pass init's check, init fails cleanly and works when rerun, and a pending push is retried to ok.
- **Health, setup and CLI** (`internal/health`, `internal/wikiinit`, `cmd/eva-md`). Doctor checks and hook-trust parsing, unknown config keys, wiki creation and adoption, and the command-line surface, whose usage line matches the dispatch. Every new doctor row in its PASS, FAIL and UNKNOWN cases from planted records (`TestUpdateRows`, the not-installed row and the `cli_missing` fix included), each notice and none when healthy, bounded tail reads, the status rows, the backlog's 4,096-entry limit (`TestBacklogListingIsBounded`) and unusable watermarks; `status` never writes and never needs a model (`TestDoctorJSONAndStatusNeverNeedModels`); `doctor --live` with fake CLIs. The names check rewrites a stale index, fails with its fix, skips another instance's wiki and reports a busy lock. Setup against temporary bare repos, with fake gh and glab scripts and a fake ssh: creating with gh and with glab and choosing between them, an existing repo used or refused, public and internal remotes refused, timeouts and a create that hangs, an address that can't be read back, the token's scope; every setup state with its exact prompts, the clone-again address, the peek's refusals, the label compared without the domain (`TestSetupKnowsThisMacWhateverItsDomain`), a clone of another repo refused (`TestSetupRefusesAFolderThatIsAnotherClone`), a repository with no remote, one with commits, an eva wiki with uncommitted changes, one whose remote was removed, one whose local remote isn't there and one with a `file://` remote refused at the folder question (`TestSetupRefusesARepoWithoutRemoteAndADirtyWiki`), a repo git reads with no sign-in, on a host no CLI can tell about, asked about with no as the default and refused without a terminal (`TestSetupAsksAboutARepoAnyoneCanRead`), that read run with no git config, `.netrc`, Kerberos ticket, proxy or prompt (`TestProbeCannotSignIn`), cloning again stopped for an empty repo or another wiki (`TestSetupClonesAMissingWikiAgain`) as init refuses it (`TestInitKeepsTheConfiguredWikiOfAnEmptyRepo`), and a folder holding only `.DS_Store` taken as empty (`TestAFolderWithOnlyDSStoreIsEmpty`). Install over an installed plugin a host refuses to add again verifies the registration instead, and its rollback does too (`TestUpgradeWhenTheHostRefusesToAddAnInstalledPlugin`). The daily commit refuses a wiki of a newer schema (`TestGuardsRefuse`) and sorts a missing signer from a declined signature (`TestMissingSignerFails`, `TestDeclinedSignatureFails`).

A few tests run real hook budgets of 100 ms or more. On a heavily loaded machine they can still fail; a rerun normally passes.

## Live checks

These were run by hand in the real host apps with synthetic test chats. Each planted a few made-up facts in one chat, then asked for them in another with tools and the host's own memory turned off, so the answer had to come from eva-md's brief.

Passed:

- **Claude Code CLI.** Recall of all planted facts in a new chat, after forced compaction (`/compact`), and after `/clear`. The answer after `/clear` was slow because of the model's reasoning effort; the hook had already delivered the facts.
- **Codex CLI and cross-host.** Facts planted in Claude Code were recalled in a new Codex chat, in a Codex chat started by a clear, and again in that chat after forced compaction.
- **Claude Code desktop app.** Recall at startup and after `/compact`. After compaction the context also held the host's own compaction summary, so this check does not prove eva-md was the only source.
- **Install through the native CLIs.** Claude Code's strict plugin validation and Codex's plugin validator passed. After the user approved the hooks in Codex `/hooks`, all seven eva-md hooks showed as trusted and enabled, and `eva-md doctor` reported no FAIL checks.
- **Transcript recovery on real hosts.** Replies missed by a hook were recovered from the known transcript without duplicates. Typed prompts in real Claude Code transcripts carry the `promptId` field that recovery relies on.

## Performance

Targets, as p95 including process start:

| Measure | Target | Measured |
| --- | --- | --- |
| Capture (one Stop hook) | 50 ms | about 25-30 ms, in a git repo and in a plain folder |
| Startup brief (SessionStart) | 300 ms | about 100-150 ms |
| Capture with transcript recovery | 50 ms | under 50 ms |
| Prompt after a brief, checking for a refresh, with 200 other projects in the wiki | 50 ms | about 25-27 ms |
| Prompt naming 3 systems, with a full names index (2,000 names), 3 pointers sent | 50 ms | about 30 ms |
| Stop that spawns an update (60 KB or more unprocessed) | 50 ms | about 27-31 ms |
| SessionEnd, spawning an update | 200 ms | about 45 ms |
| Startup brief with two days of run log and two months of commit records to check | 300 ms | about 120-130 ms |

Capture in a git repo meets its target because hooks cache each worktree's identity (see [design.md](design.md)). Without the cache, every hook started three or four git processes.

The startup brief's cost doesn't grow with the wiki or with the length of a chat. Measured with `eva-md brief` on a Mac, median of runs:

| Layout | Brief |
| --- | --- |
| Wiki of 10,000 pages (44 MB) | about 38 ms, the same as an empty wiki |
| Wiki of 10,000 pages with a stray symlink | about 39 ms, Now section still shown |
| One 200 MB session file | about 130 ms |
| 64 session files of 5 MB each | about 325 ms |

The last row is the brief's remaining cost: it decodes the last MiB of each of the 64 newest session files, so it passes 300 ms only when about 64 recent chats each exceed 1 MiB.

To measure on your machine, build the binary and run the benchmark:

```sh
go build -mod=readonly -o bin/eva-md ./cmd/eva-md
python3 -I scripts/benchmark.py --binary bin/eva-md --cwd <a git repo outside temp folders>
```

The script uses its own temporary HOME and never touches your setup. Pass a folder outside temporary folders, because hooks skip those. It clears `CLAUDE_CODE_ENTRYPOINT`, so a run from inside an agent's chat isn't taken for a program's chat. It plants three exchanges, pads the inbox to about 50 MiB, then times 10 startup briefs and 100 Claude Stop hooks that each recover a new transcript row. Then, with a wiki of 200 other projects' now pages, its schema and an instance in the config, so that updates and the daily trigger are on, and two days of run log and 60 days of commit records, it times 10 startup briefs that check them (the first spawns maintain), 100 Codex Stop hooks and 100 prompts after a brief. With 400 system pages, a map and a full names index planted, it times 100 prompts that each name 3 systems and must get 3 pointers. Last come 30 Codex Stop hooks that each spawn an update and 30 SessionEnd hooks that each spawn one. The installed binary in its temporary HOME is a stand-in that only counts its runs, so it never starts a real update, commit or model call, and the script checks for 61 spawns, maintain exactly once. It prints the p95 of each and whether it met its target. `--output <file>` also saves the report. The transcript and capture figures are sensitive to machine load, so compare two builds in alternating runs, or best of all interleaved sample by sample.

## Not verified yet

- **Codex desktop app.** Recall in a new chat and after compaction have not been checked in the Codex desktop app.
- **Real use.** A stretch of everyday use with zero hook errors and capture p95 under 50 ms, measured on an installed build.
- **Live updates.** No update has run live yet: the live resume test with the update on, the live accuracy runs, and a real `eva-md doctor --live` on each host are still to do.
- **The daily commit on real hosts.** A day's signed commit and push from a detached job, and the number of signing approvals it takes.
- **A wiki on a self-hosted GitLab.** Init, a day's commit and push, a live update on each host, and the instance guard refusing another machine's wiki. Offline tests use a fake ssh and an unreachable host only.
- **The digest skill.** `claude plugin validate --strict` with the skill, Codex loading it through the manifest's `skills` field, and the skill triggering on both hosts.
- **Host signals.** The entrypoint each Claude surface sets (one chat per surface, then its doctor row), the paste wrapper in a real hook payload, and whether `codex exec` can be told apart.
- **Setup with real gh and glab.** Offline tests use fake scripts only, and the no-sign-in read of a repo on another host is checked only to fail closed.
- **An upgrade over an installed plugin.** Install re-runs each host's add command when the plugin folders change, as this release's do; whether each host accepts it, and the fallback that accepts a registration that still verifies, are checked with fake hosts only.
- **A burst of parallel tool calls.** Whether Codex waits for its async PostToolUse hook, and how long a burst of 5 parallel tool calls waits for the session lock on each host, have not been timed.
- **Codex `mcp__` tool lines.** The Codex plugin's matcher includes `mcp__.*`; the tool names Codex reports for MCP calls have not been seen in a real payload.
