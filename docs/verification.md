# Verification

This page says what has been checked, and how. Everything built is covered by the automated tests below. The live checks cover capture, resume, the Codex feature list and plugin inventory, read without a model call, the releases on GitHub, cut from a Mac and from GitHub, and the install and uninstall scripts from one: no update has run live yet, and the live checks still owed, among them wiki updates, system pages and the code they cite, standing rules, pointers, knowledge pages and prompt recall, the digest and recall skills, the MCP server, setup with real gh, and with glab beyond one self-hosted GitLab, `eva-md upgrade` and a whole uninstall from a release, an upgrade over an installed plugin and a day's run of a wiki on a self-hosted GitLab, are listed under "Not verified yet". Open problems are listed in [known-limitations.md](known-limitations.md).

## Automated tests

Run them from the repo root:

```sh
gofmt -l cmd internal     # prints nothing
go vet ./...
go test ./...
go test -race ./...
```

GitHub Actions runs four jobs for every push to main and every pull request ([ci.yml](../.github/workflows/ci.yml)). The macOS job, the test run of record, runs the same four checks and the build. A second macOS job runs the latency gate, apart from the tests, whose load would leave it nothing to judge: it builds the binary of the commit before the change, runs `scripts/benchmark.py --compare` on it and the change's own binary, prints the report and saves it as the run's `latency` artifact. The gate is advisory for now: it reports and never fails the job, until an unchanged binary has passed it twenty times there with no fail between them ([docs/v2/baselines/README.md](v2/baselines/README.md) holds its rule, the count and the stored baseline). The Linux job runs `scripts/linux-check.sh`, which builds eva-md and runs gofmt, vet, the tests, the race detector included, and the benchmark, with the `TMPDIR` outside `/tmp` the tests need there (in CI's one-commit checkout the benchmark doesn't time the code briefs, which count commits since `HEAD~1`); it keeps eva-md building and its tests passing on Linux, where cloud sessions work on it, though eva-md itself runs only on macOS. A fourth job, `guards`, on Linux with the whole history, runs `eva-eval paths` over the commits the change brings, on their first parents. It fails the job when a commit with a `Card:` line touches a path outside its cards' `paths` blocks, names a card that does not exist or has no such block, widens its own card's block, or carries a line that sets out to name a card in another form, and it lists a commit with no such line as the lead's. It then runs `eva-eval size`, which prints the Go lines built into eva-md for macOS, the lines merged cards schedule for deletion, the net, the ceiling of 53,694 and the headroom, in a step that fails nothing: the ceiling binds at the cut-over ([docs/v2/plan.md](v2/plan.md), section 7, "Where the decisions stand"). The checks that need macOS itself run only in the macOS job: the release script's own tests (`internal/release/release_darwin_test.go`), which give it a pseudo-terminal through macOS's own calls, and the checks of a folder typed in another letter case, which need a file system that ignores case.

The evaluation build is eva-md built with the `evamd_eval` tag, for the evaluation's continuation sessions, which run scripted chats in Linux containers: its setup gets past the macOS check, and a hook run with `EVA_MD_EVAL_ACTOR=person` stores a Claude Code chat's prompts as a person's even when a program started the chat. The effect stays in the hook: the jobs a hook starts get an environment without either variable. No release carries it. `evalbuild_test.go` in `cmd/eva-md` fails if `evalbuild.go`'s build constraint is anything but the tag alone; if another file of the command names the tag or the variable; if a build without the tag compiles the file, for this machine or for any target the release workflow builds, in that workflow's environment; if a script or workflow names the tag, passes `-tags` to anything but git, go test or go vet, or sets `GOFLAGS` to `-tags` or to a value from a variable; or if the release's own build, for each of its targets, records a build tag or holds the evaluation build's code.

Every test runs against a temporary HOME with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM=1` set, so no test reads or changes the real home folder, the hosts' settings or the user's git config. The one exception is Go's own installation and its build and module caches, which `go test` itself uses: the release stand-in's build shares them, and `TestReleaseLicenses` reads the licenses and notices it checks there. A temporary HOME, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM` don't shut out git configuration carried by the environment, `GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG`, which cloud workspaces set, as to rewrite `git@github.com:` addresses to `https://github.com/`, nor a commit identity carried by the environment, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`, which a cloud environment may set to give its commits its owner's name, so every package whose tests run git clears those variables first in its `TestMain`, with `internal/testgitenv`, and the suite behaves the same with or without them. Fixtures that look like secrets are joined from fragments at run time.

## Live accuracy run

The live accuracy run checks the Wiki updates stage's accuracy target on a real host (see [design.md](design.md), "Testing"). It has not run yet. It sends each pass of the accuracy suite's 12 fact scripts through the host's real update command, as the update job does, checks and applies the answer, and prints each history's metrics and misses, with the page of each history that missed something, then the counts against the target: every enforceable obligation met, no speaker or date error, and at most 2 content obligations missed. It is a developer's command, which no release or install builds. Run it from the repo root, one host at a time, on a Mac where that host is logged in:

```sh
go run ./cmd/live-accuracy --host claude-code --spend-model-quota
go run ./cmd/live-accuracy --host codex --spend-model-quota
```

Each run makes 21 model calls on the host's subscription, one a pass, each allowed up to 10 minutes. Without `--spend-model-quota` it says so and calls nothing. `--effort` sets the effort, `highest` unless given, as for the update, and the report counts the answers at each effort the host used, since the update steps down an effort a model refuses; `--model` sets a model, the host's default unless given, and a model the host rejects stops the run at its first answer, which came from the host's default model instead; `--cli` names the CLI by its absolute path, the one on PATH unless given; and `--codex-ignore-user-config` runs Codex as `codex_ignore_user_config = true` runs the update. An effort the host lacks, a model name a CLI flag can't take and a `--cli` that names no executable file are refused before anything runs. It works in a temporary home of its own, which holds each call's empty run folder and is removed at the end, and reads and writes nothing of eva-md's: no config, state, inbox or wiki. The host CLI runs with your usual login, as the update job's calls do. An answer the update would refuse counts as a content obligation missed, and so does each fact its chat says or ends. Progress goes to stderr and the report to stdout. It exits 0 when the run meets the target, 1 when it misses it or stops, as on an auth failure, a rate limit, a timeout or a rejected model, which judge nothing, and 2 when it refuses to run, as on any usage error. One run is one sample of a model's answers, and the rule and knowledge histories run offline only.

To keep a run's answers, give it `--record` with a file that does not exist yet, and `--pages` with a folder that is new or empty:

```sh
go run ./cmd/live-accuracy --host claude-code --spend-model-quota --record answers.jsonl --pages pages
go run ./cmd/live-accuracy --host claude-code --replay answers.jsonl --pages pages-again
```

The recording is one JSON line a pass, written as the run goes: the host, the model asked for, the effort the answer came at, the script and pass, the answer's JSON or null, and the runner's reason, and nothing of the machine, the account or a path; it does hold the model's name and its answers to the suite's made-up chats. `--replay` answers each pass from it, calls nothing and needs no `--spend-model-quota`; given the run's `--effort` and `--model`, it prints the report the run printed and exits as it did. The recording keeps the effort each answer came at, not the one the run asked for, so a replay without `--effort` says the effort is `as recorded` in the report's first line. It refuses, before anything runs and with exit 2, a recording of another host, model or format version, one with a reason the update does not know, a line with a key missing, added, given twice or of another type, null among them, and one that lacks a pass of the suite or holds one twice, as the recording of a run that stopped part way lacks the passes after the stop. `--pages` writes each script's page after its last pass, as `v1.NN.md`, the pages the evaluation harness's `eva-eval fidelity --pages <dir> --out <dir>` scores into v1's fidelity rows; a replay writes the same pages byte for byte. A page that cannot be written stops the run before its next call, and the run exits 1.

To keep what each pass cost and what the host printed, give it `--trace` with a folder that is new or empty, and to have a pass that times out counted as a refused answer, where it would stop the run, `--timeout-refused`:

```sh
go run -buildvcs=true ./cmd/live-accuracy --host claude-code --spend-model-quota --timeout-refused --record answers.jsonl --trace trace
go run ./cmd/live-accuracy --host claude-code --replay answers.jsonl --timeout-refused
```

The trace is written as the run goes, each line synced. `run.json` holds the host, the effort and model asked for, the version of the CLI the run starts, as the host adapter reads it, eva-md's commit and whether its tree had changes, which a build records only with `-buildvcs=true` (`go run` leaves the commit empty without it), whether `--timeout-refused` was given, and the run's UTC date. `passes.jsonl` has a line a pass the runner answered: the call's milliseconds, the tokens in, cached ones included, and out, the attempts, the effort the answer came at, the model the host says answered, the model note, the degraded note, the runner's reason, and why the run counts the answer refused, when it does: the runner's reason, `timeout` under `--timeout-refused`, or the validator's error. `raw/` holds what the CLI printed on stdout and stderr on each attempt, as `SS-PP-AA.out` and `.err` for script, pass and attempt. `end.json`, written last, also when the run stops or is interrupted, says whether the run met the target, missed it or stopped, why it stopped, and how many passes it traced, refused and timed out. A run that stops keeps the trace of every pass up to and with the one that stopped it. Its JSON files hold no path, no time of day and nothing of the machine, but the trace holds model names, host ids and the host's raw output, which can name a plan and a rate limit's reset time: hand it over privately, and never commit it as written. `--trace` is refused, before anything runs and with exit 2, for a folder that holds anything, is the pages folder or holds the recording, and with `--replay`, which calls nothing. With `--timeout-refused` the run prints the existing timeout line on stderr, counts the pass refused and goes on, and its report says `answers timed out: n` after `answers refused`; the recording and the trace keep the pass's `timeout`, and `--replay` with the flag counts a recorded timeout the same way, so it prints the run's report and writes its pages. Without the flag a run, or a replay, stops on a timeout.

| Startup brief with 64 newer chats a program ran, 2 MiB of short tool lines and replies | 300 ms | about 170 ms in one run with other jobs running (load average 4 to 12), against 168 ms for the same run's brief without them |
| Capture with transcript recovery | 50 ms | under 50 ms |
| Prompt after a brief, checking for a refresh, with 200 other projects in the wiki | 50 ms | about 25-27 ms |
| Prompt naming 3 systems, with a full names index (2,000 names), 3 pointers sent | 50 ms | about 30 ms |
| Stop that spawns an update (60 KB or more unprocessed) | 50 ms | about 27-31 ms |
| SessionEnd, spawning an update | 200 ms | about 45 ms |
| Startup brief with two days of run log and two months of commit records to check | 300 ms | about 120-130 ms |
| Startup brief pointing at 3 systems that cite the project's code at HEAD~1, counting it (3 git calls) | 300 ms | about 105 ms; the counts add about 25-30 ms |
| Prompt naming 3 systems, each pointer with its code note from a code status of 400 pages | 50 ms | about 35-37 ms, about 1 ms over the same prompt without notes |
| Prompt recalling 3 facts from a full recall index (1,678 rows, 512 KiB), beside the full names index | 50 ms | about 31 ms; recall's own read and scoring take about 3 ms |
| MCP server: a cold start to its `initialize` answer | 100 ms | about 14 ms |
| `eva_search` over the 50 MiB inbox, a wiki of 200 projects and 400 system pages | 5 s | about 0.11 s |
| `eva_show` of a source ref the search found | 300 ms | about 6 ms |
| `eva_status` with the run log and commit records above | 300 ms | about 70 ms |
| MCP server's exit once its stdin closes | 1 s (the slowest of 10) | about 1 ms |

Capture in a git repo meets its target because hooks cache each worktree's identity (see [design.md](design.md)). Without the cache, every hook started three or four git processes.

The startup brief's cost doesn't grow with the wiki or with the length of a chat. Measured with `eva-md brief` on a Mac, median of runs:

| Layout | Brief |
| --- | --- |
| Wiki of 10,000 pages (44 MB) | about 38 ms, the same as an empty wiki |
| Wiki of 10,000 pages with a stray symlink | about 39 ms, Now section still shown |
| One 200 MB session file | about 130 ms |
| 64 session files of 5 MB each | about 325 ms |

The last row is the brief's remaining cost: it decodes the last MiB of each of the 64 newest session files, so it passes 300 ms only when about 64 recent chats each exceed 1 MiB.

To measure on your machine, build the binary and run the benchmark:

```sh
go build -mod=readonly -o bin/eva-md ./cmd/eva-md
python3 -I scripts/benchmark.py --binary bin/eva-md --cwd <a git repo outside temp folders>
```

The script uses its own temporary HOME, under /tmp so the binary's path that every pointer names is near an installed one's length, and never touches your setup. Pass a folder outside temporary folders, because hooks skip those. It clears `CLAUDE_CODE_ENTRYPOINT`, so a run from inside an agent's chat isn't taken for a program's chat. It plants three exchanges, the first event spawning the day's maintain, as on an install without a wiki, pads the inbox to about 50 MiB, then times 10 startup briefs, 10 more with 64 newer chats a program ran beside the person's, each 32 KiB of short tool lines and replies with quotes and line breaks, 2 MiB in all, the most the brief reads beyond its 64 files, which must not push the person's chat out of the brief and which the script then removes, and 100 Claude Stop hooks that each recover a new transcript row. Then, with a wiki of 200 other projects' now pages, its schema and an instance in the config, so that updates and the chat start's push-retry check are on, and two days of run log and 60 days of commit records, it times 10 startup briefs that check them, the first of which also asks for the day's sweep, giving the hook's day, which the script then records as the day it was taken, as the job would, 100 Codex Stop hooks and 100 prompts after a brief. With 400 system pages, a map and a full names index planted, it times 100 prompts that each name 3 systems and must get 3 pointers. Then come 30 Codex Stop hooks that each spawn an update and 30 SessionEnd hooks that each spawn one. The installed binary in its temporary HOME is a stand-in that only counts its runs, so it never starts a real update, commit or model call, and the script checks for 62 spawns, maintain and the sweep exactly once each. A hook that misses its time limit delivers nothing by design, neither its spawn nor its output, so the script lets a Stop's or a SessionEnd's spawn be missing, and passes over the empty output of a prompt or a Codex Stop while no more than one hook in twenty of its loop passed the limit, only for a hook it timed itself at that limit less the 10 ms the hook keeps for its output, and prints beside its report how many hooks of each timed loop passed it. Then it times the code notes: 10 startup briefs that point at 3 systems citing the `--cwd` repo at HEAD~1, so each brief counts the commits since, and every pointer must say the code moved (a repo with a single commit skips these); and 25 prompts that each name 3 of the 400 systems, whose map lines cite a made-up repo's code and whose entries in a planted code status of all 400 pages say it moved, and every pointer must say so. Then it fills the recall index to just under its 512 KiB bound, 1,678 facts, and times 25 chats of 4 prompts, each asking about 3 facts it has not had by their numbers, and every prompt must get the label, the fence and the 3 fact lines in at most 1,000 characters, the facts being another project's that a planted repos index makes a sibling of the checkout's, so every prompt reads that index too. It prints the p95 of each and whether it met its target. It also reports, as figures only, the time of `eva-md search --all --days 0` over the padded inbox before and after `eva-md index`, the first including the search's own top-up of the index, and the time `eva-md index` took: about 120 to 240 ms before, about 120 to 160 ms for `eva-md index` and about 30 ms after, process start included. The padding is events, which are never indexed, so the figures say little about a real inbox. `--output <file>` also saves the report. The transcript and capture figures are sensitive to machine load, so compare two builds in alternating runs, or best of all interleaved sample by sample.

After the spawn hooks, and before the code notes and recall, the benchmark starts the MCP server in the `--cwd` folder ten times, each timed to its `initialize` answer and to its exit once stdin closes, then times 20 `eva_search` calls for the planted word over the padded inbox, 20 `eva_show` calls of the ref it found and 20 `eva_status` calls on one server. It checks each answer, and that the server writes nothing to stderr.

The benchmark's scenarios run from a list: each is a file in `scripts/bench/` that adds itself, and `scripts/benchmark.py` loads them by path. Beside the padded inbox above there are three more: the start of the process on each host's launch path, which every hook figure includes (Codex's hooks run through `/bin/sh -c`, as its declaration does); the shape of the one real install, an inbox of 600 session files and a wiki of 54 pages, with a chat start, a prompt, a capture and the brief built by command; and one turn of 50 tool calls on each host's hook declaration, with the processes it starts and the milliseconds it sums.

`python3 -I scripts/benchmark.py --compare OLD NEW --cwd <repo>` is the latency gate. It runs both binaries in alternating runs on one machine, each twice a round, and exits 1 when the new one is slower than the machine's own noise allows or fails a scenario the old one passes, 0 with `not judged` when the machine was too noisy to tell, and 2 when it could not run. Its rule, and why each part of it is there, are in [docs/v2/baselines/README.md](v2/baselines/README.md); its decision is a pure function of the samples, tested with made-up numbers by `python3 -I scripts/bench/test_gate.py`, which the gate's job runs first. On the Linux machine it was built on, an unchanged binary passed 19 gates of 20 by its first rule and the other was not judged, while the machine's disk was busy with other work; a binary with 20 ms added to capture failed on 14 figures. Worked out again by the second round's rule, the same 20 gates pass 16 times and are not judged 4 times, and the one with 20 ms added fails on 12 figures.
