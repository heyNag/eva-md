# eva-md: instructions for coding agents and contributors

eva-md is the platform for eva.md ("Eva dot M D"), a Markdown, git-based memory for Claude Code and Codex. Hooks capture chats into a redacted local inbox and give new chats a resume brief. The long-term memory lives in a separate private wiki repository that `eva-md setup` creates in a folder the user chooses. This repo is the platform only; it never contains wiki content.

Capture, resume and wiki updates are built: the background update job and its triggers, which summarize chats into thread pages, the daily signed commit and push, `doctor --live`, system pages and how far the code they cite has moved, standing rules and per-prompt pointers, knowledge pages the update promotes, with recall of matching knowledge on prompts, the project's constraints in the brief and a recall skill, a search index, a command that removes captured chats from the inbox, a read-only command that scores what eva-md captured against the hosts' own records, a report of how eva-md has behaved in counts and durations only, and a read-only MCP server the plugins declare, and for eva-md's developers a live accuracy run of the update. Support for a wiki on a self-hosted git server, such as a self-hosted GitLab or a GitHub Enterprise server, is built too, and so are releases, cut from GitHub or from a Mac, the one-command install and upgrade from them, and uninstall. All of it is checked offline, with fake host CLIs and a fake GitHub. Releases are published, cut from a Mac and, since 2026.11.5, from GitHub, and the install command from one has set up eva-md and a wiki on a self-hosted GitLab. The live checks on real hosts, `eva-md upgrade` and a whole uninstall from a real release, the first live updates, a day's run against that wiki and the first live accuracy runs are still pending.

## Layout

- `cmd/eva-md`: the CLI. `main.go` dispatches commands through the command table in `table.go`, which lists every command with the file that holds it, and every file that supports them with what it holds; a new command is a new file that registers itself there, and a test fails on a file of the CLI neither list names. `rosetta_other.go` stands in for upgrade's Rosetta check, in `rosetta_darwin.go`, off macOS, so eva-md builds on Linux. `timelimits.go` holds the time limits tests raise, which `timelimits_raised.go` raises as a build with the `evamd_testlimits` tag, the tests' release stand-in, starts. The stand-in also sets `hostOS` to darwin, as `TestMain` does, so setup's macOS check passes on Linux too. `evalbuild.go` is the evaluation build (tag `evamd_eval`), which no release carries (`evalbuild_test.go`).
- `internal/`: one package per concern, such as `hook`, `inbox`, `catchup` (transcript recovery), `resume`, `redact`, `install` (the stable binary, the plugins, the install record and the link on PATH), `release` (eva-md upgrade's releases), `health`, `config`, `paths`, `identity`, `session`, `wikiinit`, `okfadapter`, `threadpage` (the thread and rules page model), `freetext` (the anti-forgery cleaning the brief and the update input share), `update` (wiki updates), `systempage` (system pages, the system map, and the names and repos indexes), `knowledgepage` (knowledge pages, their map, the recall index, and recall's scoring and scope), `coderef` (how far the code a system page cites has moved), `wikigit` (the git runner, the daily commit and the push), `lint` (the daily wiki lint), `mcp` (the read-only MCP server), `testlimits` (the time limits tests raise) and `testgitenv` (tests only: it clears the git configuration and identity the environment carries).
- v2's packages, built beside v1 with no caller yet or behind a switch that defaults to v1's behaviour, each with its contract in a `SPEC.md` beside it or in its card: `internal/ledger` (the event model and the one reader of captured chats, with `ledger/audit` and `ledger/shapes`, behind `eva-md audit capture` and `audit shapes`, which print numbers only, and `ledger/registry`, the project id), `internal/store/profile`, `store/codec`, `store/conformance` and `store/migrate` (the format's checker, the one reader and writer of a document's bytes, the properties every store is held to, and the migrator), `internal/work` (the worker), `internal/host/adapter` (the one place that knows a host), `host/capture` (the hook payload decoder), `internal/derive/modelrun` (a sealed model call to a host's CLI), `internal/eval` with `cmd/eva-eval` (the evaluation's results store, scenarios, fidelity scorer, retrieval scorer, gates, v1's row, the continuation tasks and driver, the pilot's tasks, the contract spike, CI's `guards` checks and the size ledger in `eval/guard`, and its command, which no release builds), and `internal/hostfacts` with `cmd/hostrec` (the host sittings' recorder), and `internal/spec` (tests on `docs/spec/` and `docs/decisions/`). Tests' fakes: `internal/ledger/ledgertest`, `ledger/registry/registrytest`, `internal/store/storetest`, `internal/eval/retrieval/retrievaltest`, `internal/host/hostfake`.
- `cmd/live-accuracy`: the live accuracy run, a developer's command that no release or install builds. It runs the accuracy suite's 12 fact scripts on one host's real update command through `internal/update/accuracy/live`; the scripts and their measures are in `internal/update/accuracy`, which nothing in eva-md imports. It needs `--host` and `--spend-model-quota`, and its `--trace` folder holds the host's raw output: never commit one (docs/spec/live-accuracy.md).
- `scripts/benchmark.py`: the offline latency benchmark. Its scenarios are files in `scripts/bench/` that add themselves to its list, and `--compare OLD NEW` is the latency gate, which a macOS job of CI runs on every change; `scripts/bench/test_gate.py` tests the gate's decision on made-up numbers, and `docs/v2/baselines/` holds its rule and the stored baseline.
- `scripts/linux-check.sh`: the checks in "Before you finish a change", run on Linux, in a cloud session and in CI's Linux job. `scripts/linux-gate.sh` runs the latency gate there the same way, on the binary of an earlier commit and the working tree's. `scripts/linux-space.sh` shows what the checks have left on disk, and with `--prune` frees it.
- Releases: `.github/workflows/cut-release.yml` (Cut a release, which the maintainer runs to release from GitHub: it plans the release, waits for an approval in the `release` environment, pushes an unsigned tag, calls the release workflow and checks what it published), `scripts/release.sh` (the release from a Mac, the fallback, which makes a signed tag; its `--plan` mode makes the same checks for Cut a release, but the signing check, and gives it the tag and notes), `.github/workflows/release.yml` (the workflow a pushed tag runs, or Cut a release calls with its tag through `workflow_call`, which builds, verifies, attests and publishes) and `internal/release`, which finds, downloads and checks a release for `eva-md upgrade` and holds the tests that run the release script against a temporary origin and a fake gh, on macOS only, and those that check the workflows, which run on Linux too.
- `scripts/install.sh` and `scripts/uninstall.sh`: the one-command install, upgrade and uninstall, published with each release. They run on macOS's `/bin/bash` 3.2, so they use no bash 4 features. `cmd/eva-md/release_test.go` builds a release stand-in and runs both scripts against it.
- `scripts/LICENSES.txt`: the licenses published with each release: eva-md's, then those of the modules built into the binaries, Go's, and the notices in Go's own code that ask to go with a copy of the program. `cmd/eva-md/licenses_test.go` fails when one is missing and gives the text to add.
- The search index: `internal/searchindex` (its segment format, refresh, merge, catch-up and queries), `internal/inbox/walk.go` (the walker it reads session files with, and the trust check it shares with search), `internal/paths/lock.go` (the lock helper its writers take), `internal/resume/search_index.go` (how search reads it) and `cmd/eva-md/index.go` (`eva-md index` and maintain's index step).

## Rules

- **Go and dependencies.** Module `github.com/heyNag/eva-md`, `go 1.26.0`. There are only two dependencies: okf (`github.com/okf-memory/okf-agent-memory` v0.8.0), imported only by `internal/okfadapter`, and `github.com/BurntSushi/toml`, imported only by `internal/config`. Don't add others.
- **okf stays pinned and unpatched.** Use it as a library at the pinned version. Never patch or vendor-modify it; the one exception is a temporary `replace` to a local fork to apply a security fix, as docs/spec/okf-adapter.md's upgrade policy allows. Build what it lacks inside eva-md; that spec lists the gaps.
- **Only eva's name shows.** eva.md is the front-facing name. Never show okf's name, or any library's, in what a person sees: command output, doctor rows, messages and errors, the run log, the README, the plugins or the files a new wiki gets. The exceptions are okf's own temporary files, `.tmp-okf-*`, and its lock file, `.okf-write.lock`, which eva-md can't rename without patching okf, and each release's `LICENSES.txt`, which must carry the license of every module built into eva-md. The docs credit okf.
- **Never change `internal/redact/baseline`.** It holds the frozen baseline redaction rules. By default `redact.Redact` removes the union of what the baseline rules and the current rules remove, so a change to the current rules can never keep a secret the baseline rules remove. The switch `redaction_current_rules_only` runs the current rules alone and stays off, since they keep secrets in shapes of code that the baseline rules remove, which `TestOracle` records as gap classes. Improve redaction in the current rules in `internal/redact`.
- **Hooks fail closed and stay fast.** A hook must exit successfully on any failure, never block the host, and make no network calls. Keep within the latency targets: capture p95 under 50 ms, startup brief p95 under 300 ms.
- **Tests never touch the real machine.** Use `t.TempDir()`. Set `HOME`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM=1` in tests. Those don't shut out git configuration carried by the environment (`GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG`), which cloud workspaces set, or a commit identity carried by the environment (`GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`), which a cloud environment may set, so every package whose tests run git calls `testgitenv.Clear()` first in its `TestMain`; a new such package does the same. Never read or write the real home folder, `~/.claude`, `~/.codex`, eva-md's real config or state, a real wiki, or the user's git config. The one exception is Go's own installation and its build and module caches, which `go test` itself uses: the release stand-in the end-to-end tests build shares them, in a home of its own with `GOENV=off`, and the licenses test reads the licenses and notices it checks there.
- **Tests never depend on machine speed.** CI runs on a slow macOS virtual machine, so a test may fail only when behaviour is wrong. Tests raise the production time limits once, in `TestMain`, through their variables (`internal/testlimits` raises the exported ones), and hook tests set `Slack`. A test of a time limit makes the slow side block until the test releases it or the limit's context ends, or ends the limit's time at an exact point, and bounds wall-clock time from above only with a hang guard of 30 seconds or more; a test that needs a short limit gives it to one value only, never by changing a package variable. No sleep or time window decides an outcome, or what a test can catch. Never skip or retry a test to get it to pass.
- **Tests are written for macOS, where they are judged.** CI's macOS job is the run of record, and a cloud session cannot run it. macOS reaches its temporary folders through an alias (`/var` for `/private/var`), so a test that compares a path under `t.TempDir()` with one that git or the system resolved resolves its own first, with `filepath.EvalSymlinks`. Its file system does not tell letter case apart, so no test leans on two names that differ only in case. After a push, read CI's result for that commit, on macOS and on Linux, with `gh run list --commit <sha>` and `gh run view <id> --log-failed` where gh is there, or with the session's own GitHub tools, and fix a failure forward at once. A green run says nothing of the latency gate, whose step is advisory: its verdict is in that step's log or in the run's `latency` artifact.
- **The repository is public.** Its documents, code, tests, fixtures and commit messages speak of a self-hosted GitLab, GitHub or a GitHub Enterprise server, never of where anyone is employed; `TestThePublicRepoUsesNeutralWording` holds the words it bans and reads every document, script and workflow. Nothing in it names a person, says which model the owner uses with eva-md, or says more of the machine eva-md really runs on than "the one real install (a Mac whose wiki is on a self-hosted GitLab)" and the counts of its first field report already in plan section 13 and `scripts/bench/real_install.py`: counts and shapes, never a name, a path, a chat's text or a model's name. A report from that machine, and anything else taken from it, stays out of the repository. A commit message names no model or assistant; the trailer a commit carries is given by the session that makes it and is not part of this rule.
- **Don't run setup, init, install, uninstall, upgrade, the install or uninstall scripts, update, commit, maintain, system write, inbox clear --apply, doctor --live, the live accuracy run or an `eva-eval` run with `--spend-model-quota` against the real machine** unless the person you are working for asks. Setup, init, install, upgrade, the scripts and uninstall change host plugins, create and push a wiki, or remove an installation; update, doctor --live, the live accuracy run and those `eva-eval` runs make real model calls on the user's subscription or keys; update and system write change the real wiki, and commit and maintain commit and push it; inbox clear --apply deletes captured chats from the real inbox, with no undo. Use `install --dry-run`, `uninstall` without `--apply`, `upgrade --check`, `inbox clear` without `--apply` and `update --dry-run --session <host>:<id>` to preview. When you are asked to change host plugins, use the hosts' native commands, preserve unrelated settings, and never grant Codex hook trust on the user's behalf.
- **Never print, log or commit secrets.** Test fixtures use made-up values. Don't log captured content; report counts instead.
- **Don't commit or push unless asked.** Never disable commit signing or switch git identity to make a command succeed.
- **During the v2 build the owner has given standing leave.** Since 2026-11-10 the build commits and pushes to `main` directly, with no pull request and no further approval. Since 2026-11-11 a push no longer waits for the checks below: the owner has set that aside for now, so work is pushed to `main` as it is committed, the checks run after it, and a failure is fixed forward at once. The leave covers the build only: the lead and the builders, reviewers and fixers its orders name. Within it only the lead pushes to `main`; a builder, reviewer or fixer commits on its own branch and never pushes. Any other agent follows "Don't commit or push unless asked". The leave does not cover a release: never push a tag or start Cut a release unless the owner asks for that in so many words, and no push to `main` cuts one. It does not cover live runs on the owner's machines or accounts, or anything the rule above on the real machine forbids.
- **Releases are cut only with the Cut a release workflow or `scripts/release.sh`.** Never create or push a release tag, start Cut a release, even as a dry run, or run the release script without `--dry-run` or `--plan`, unless the person you are working for asks for that in so many words. Before a release from a Mac, show them the exact tag, as `scripts/release.sh --dry-run` prints it. A release from GitHub shows them the tag in its run's summary before they approve.
- **The search index is a cache, never the truth.** It is built from the inbox and can be deleted at any time; search reads every line it proposes again from the inbox before showing it, and scans what it doesn't cover. Hooks never read or write it, and nothing said off the record may reach it.

## Working in a Linux cloud session

eva-md runs only on macOS, and CI's macOS job is the test run of record. It also builds, and its tests run, on Linux, so a cloud session can work on it. Setup still refuses any system but macOS, and the tests that need macOS itself, such as the release script's, run only there.

- **Start from `main` as the remote has it:** `git fetch origin main`, then `git merge --ff-only origin/main`, which never discards anything; if it refuses because your branch has commits of its own, rebase on `origin/main`. Never `git reset --hard` over changes `git status` shows.
- Run `scripts/linux-check.sh` from the repo root instead of the plain commands. On Linux the tests need a `TMPDIR` outside `/tmp` and `/var/tmp`, whose folders eva-md's hooks skip as temporary, and a user other than root, since about 20 tests fail by design for root; the script gives them both, and when started as root, as in a cloud session, it runs the tests as an unprivileged user on a snapshot of the working tree; that user, `eva-md-check`, and the world-readable module cache it reads, `/var/cache/eva-md/gomod`, are kept for the next run, even on a machine of your own run with sudo. Arguments go only to the two `go test` runs, so a session can test a subset, as `scripts/linux-check.sh -run TestX ./internal/hook`, but gofmt, vet, the build and the benchmark still run in full.
- A change to a hook, or to anything a hook runs, is compared with the commit before it by `scripts/linux-gate.sh [BASE]`, which runs `scripts/benchmark.py --compare` as `linux-check.sh` runs the benchmark, and keeps the report in `bin/latency-gate.json`. It times hooks, so on a busy machine it says `not judged` (see Load). CI's `latency` job, on macOS, is the gate's run of record.
- **Disk.** A cloud session has a fixed allowance of disk, far smaller than the disk `df` names; `df -h /` shows what is left of it. When it is spent every write fails, and the machine may be restarted. The checks are what spend it: Go's build cache holds each package under the folder it was built in, so every snapshot and every worktree adds its own, and a cache that is kept only grows. `linux-check.sh` therefore keeps a run's build cache with its snapshot and removes both. A run holds its space until it ends, so it refuses to start unless 2,500 MB are free plus 2,000 MB for each check already running. `scripts/linux-space.sh` shows what uses the space, and `--prune` frees build cache entries no build has used for 100 minutes and snapshots a killed run left behind. Never remove a cache by hand while a check runs.
- **Load.** Several checks at once put the load at many times the CPUs. The tests still pass, since none depends on speed (linux-check.sh gives each package 60 minutes, past go test's own 10; a `panic: test timed out` there is load too). The benchmark, the script's last step, can then fail with an empty or invalid hook output or a missed target, and the latency gate says `not judged`: neither says anything about the code. Run it again when the first load figure `uptime` gives is below the number `nproc` prints, and never change code or a test to chase it.
- **Restarts.** A cloud machine can be restarted without warning. Running commands and their agents' unfinished reports are lost; files on disk have survived a restart, but only commits are counted on. Commit each time the work reaches a working state, on a branch of your own (if you have not been asked to commit, ask before long work), and make a long job one that can be started again where it stopped.
- **A script that is running is not edited.** bash reads a script as it runs it, so a change under a running script breaks that run part way. Nor is the working tree changed while `linux-check.sh` runs: its gofmt, vet and build steps, and so the benchmark, read the checkout itself, not the snapshot the tests run on.
- **Scratch files go in a folder of your own**, named for your task, under the session's scratchpad, never another agent's.
- **Scripts, workflows and documents have tests that read them.** Before you push a change to one, run the ones that take seconds. `go test ./cmd/live-accuracy ./cmd/eva-eval ./internal/release` read `scripts/` and `.github/workflows/`: every `go build`, `go install` and `go run` there must build `./cmd/eva-md` alone, with the package as the last word of its command (a `)` straight after it reads as part of its name), and no script or workflow may name live-accuracy, eva-eval or internal/eval, but for the two `go run ./cmd/eva-eval` lines of CI's `guards` job. `go test ./cmd/eva-md -run 'Design|Agents|Usage|Verification|Wording|Document'` read `AGENTS.md`, `README.md`, `docs/`, `scripts/` and `.github/`, `go test ./internal/store/profile -run TestSpec` reads `docs/v2/plan.md`, `docs/v2/working-papers/design/` and `docs/spec/store-format.md`, and `go test ./internal/spec` reads `docs/spec/`, `docs/decisions/` and the three indexes. These read files only, so they pass as root too, where the hook tests do not. `TestSweepListsTheNewestLeftChatsOfAnyProject` reads `docs/known-limitations.md` and fails as root: run it with `scripts/linux-check.sh -run TestSweepListsTheNewestLeftChatsOfAnyProject ./internal/update`. A change to `scripts/benchmark.py` or `scripts/bench/` also runs `python3 -I scripts/bench/test_gate.py`. `TestInstallScriptVersionPinThroughThePipe` in cmd/eva-md checks that README.md and `scripts/install.sh` show the same pinned install command; it builds a release stand-in, so run it the same way, on `./cmd/eva-md`.
- The tests need git 2.44 or newer and `ssh-keygen`. The cloud environment's setup script in README.md's "Development" installs both.
- Never change code or tests to make a failure seen only on Linux go away, and never skip a test there: report the failure.

## Before you finish a change

Run all of these from the repo root. Each must pass, and `gofmt -l` must print nothing.

```sh
gofmt -l cmd internal
go vet ./...
go test ./...
go test -race ./...
go build -mod=readonly -o bin/eva-md ./cmd/eva-md
python3 -I scripts/benchmark.py --binary bin/eva-md --cwd "$PWD"
```

The benchmark uses an isolated temporary home. `--cwd` must be a git repository outside temporary folders, such as this checkout. Its transcript-recovery figure is sensitive to machine load, so compare builds in alternating runs.

On Linux, run `scripts/linux-check.sh` in their place: it runs these same checks, and fails when any of them does.

If a change alters behaviour, write it in its spec's `## Since the split` (a decision in a dated record) and, where it applies, in README.md (commands, flags, config keys, setup steps), docs/known-limitations.md and docs/releasing.md, in the same change.
